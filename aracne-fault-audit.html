How to read this

Every entry names its requirements — the conditions that have to hold for the defect to fire, because most of these are corner cases rather than everyday paths — then its effect and a fix.

Two labels carry real information and are not decoration. reproduced means a reproducer was written, run against this checkout, and its output is quoted verbatim in the entry. read means the defect was established by reading the code and its call sites, with no runtime proof. Nothing was changed: the reproducers were temporary test files, run and deleted, and git status is as it was.

The whole test suite passes. Every finding below is therefore a gap in coverage as much as a gap in the code, and several sit in subsystems whose own doc comments describe the correct behaviour the code does not implement — those are called out where they occur, since the intent is already written down and only the implementation is missing.

A-01criticalreproducedfixed

Three bug and caller queries bypass the SQLite lock and retry wrappers

internal/helper/db.go:850 GetCallers · :888 ReadBugs · :927 UpdateBugState

Requirements
Any concurrent access to topology.db while one of these three runs. The bug pipeline is the designed way to produce that: bug-judge and bug-solver fan out as parallel sub-agents, each calling bug acknowledge / bug dismiss (UpdateBugState) and bug list (ReadBugs), while the guard's pre-tool scan writes the graph in front of every one of their tool calls.
Effect

Every other database entrance goes through withSQLiteRead / withSQLiteWrite, which take a per-database RWMutex, run ensureSQLiteMigrated, set PRAGMA busy_timeout = 10000, and retry eight times with backoff on SQLITE_BUSY. These three call sql.Open directly and get none of it — no mutex, no retry, no migration, and (per A-02) no busy timeout either, so they fail on the first collision instead of waiting.

UpdateBugState is the serious one because it is a write: a lost acknowledgement in a fan-out is a bug the pipeline believes it triaged. ReadBugs additionally skips the migration, so it is the one reader that can hit no such table on a database every other path would have migrated first. Both also drop per-row Scan errors with continue and never check rows.Err(), so a truncated read returns a short list as a successful one.

Evidence

A locked writer holds a transaction for 700 ms; UpdateBugState runs against it. A call on the locked path would have waited and retried:

UpdateBugState during a concurrent write transaction:
  err=database is locked (5) (SQLITE_BUSY)

And on a database with no schema, proving the migration bypass:

ReadBugs on a schema-less database:
  SQL logic error: no such table: bugs (1)
Fix
Move all three into the wrappers, which is a mechanical change — DeleteBug and DeleteAllBugs next to them are already the model: 
func UpdateBugState(dbPath, bugID string, state domain.BugState) error {
    return withSQLiteWrite(dbPath, func(db *sql.DB) error { … })
}
func ReadBugs(…) ([]domain.KnownBug, error) {
    err := withSQLiteRead(dbPath, func(db *sql.DB) error { … })
}
While there, replace continue on a scan error with a returned error and add rows.Err(). A lint or a small test asserting that no sql.Open appears outside sqlite.go would keep the next one from being added.
Landed

Fixed in helper/db.go, helper/sqlite.go. GetCallers, ReadBugs and UpdateBugState now run inside withSQLiteRead/withSQLiteWrite, so they take the per-database mutex, run the migration and retry on SQLITE_BUSY like every other entrance. Each also returns scan errors instead of skipping the row with continue, checks rows.Err(), and resets its accumulator per attempt so a retried callback cannot concatenate a partial read onto a complete one. Regression: TestBugStateWritesWaitForAConcurrentWriter holds a write transaction open and asserts the bug write queues behind it — it fails on the old code with SQLITE_BUSY.

A-02criticalreproducedfixed

Both SQLite DSN parameters are silently ignored by the driver

internal/helper/sqlite.go:92 openSQLite · same DSN repeated at db.go:850, :888, :927

Requirements
None — it is true on every open. openSQLite builds "%s?cache=shared&_busy_timeout=%d", and the three functions in A-01 add ?cache=shared&_journal_mode=WAL.
Effect

Those are mattn/go-sqlite3 parameter names. This project uses modernc.org/sqlite, whose applyQueryParams reads only _pragma, _time_format, _time_integer_format, _timezone, _txlock and vfs. Everything else is discarded without an error, so the parameters look like configuration and are dead text.

openSQLite survives this because it issues PRAGMA busy_timeout and PRAGMA journal_mode = WAL explicitly afterwards. The three raw openers do not, which is exactly why A-01 fails immediately rather than blocking: they are running with busy_timeout = 0. Shared cache is not in force anywhere.

Evidence
sql.Open("sqlite", db+"?cache=shared&_busy_timeout=10000")
PRAGMA busy_timeout  ->  0
Fix
Spell them the way the driver reads them, or drop them. The _pragma form is the one this driver honours and it applies busy_timeout first by design: 
dsn := fmt.Sprintf("%s?_pragma=busy_timeout(%d)", dbPath, sqliteBusyTimeoutMillis)
Then A-01's fix inherits the timeout automatically rather than depending on the follow-up Exec. Decide separately whether shared cache is actually wanted — with SetMaxOpenConns(1) it buys nothing, and deleting it is honest.
Landed

Fixed in helper/sqlite.go. The DSN is now _pragma=busy_timeout(N), the spelling modernc.org/sqlite actually reads, so every connection the pool opens carries the timeout — including one opened later to replace a dropped one. cache=shared is deleted rather than re-spelled: with SetMaxOpenConns(1) there is no second connection for a cache to be shared with. The explicit PRAGMA busy_timeout stays as the belt to the DSN's braces, with a comment saying which is which. Regression: TestOpenSQLiteAppliesBusyTimeout reads the pragma back off a real connection.

A-03criticalreproducedfixed

Plan Mode is bypassed by naming a path outside the workspace

internal/chat/permissions.go:40 PermissionPolicy.Decide, the outside-workspace test at :44 precedes the Plan Mode test at :47

Requirements
features.chat on, a session in Plan Mode, and a bash, edit or write call naming an absolute path outside the workspace root. Approval mode is irrelevant — the deny it should hit is unconditional.
Effect

The checks run in the wrong order. referencesOutsideWorkspace returns ask, and ask returns immediately, so the Plan Mode deny below it never executes. The result inverts the intended safety gradient: a mutation aimed inside the workspace is refused outright, and the same mutation aimed at the rest of the filesystem is merely put to the user for approval.

Plan Mode is the mode a user selects specifically to be sure nothing is executed. This is the one path where it does not hold.

Evidence
plan-mode bash inside  workspace -> deny (tool is not allowed in Plan Mode)
plan-mode bash outside workspace -> ask  (access outside workspace scope: /etc/nginx)
plan-mode write to /etc/hosts    -> ask  (access outside workspace scope: /etc/hosts)
Fix
Evaluate denials before escalations. The mode gate is a hard rule and the scope gate is a prompt, so the hard rule has to be first: 
if mode == ModePlan && (isMutatingTool(toolName) || toolName == "bash") {
    return permissionDecision{Action: permissionDeny, …}
}
if outside, path := p.referencesOutsideWorkspace(args); outside { … }
The general rule worth encoding in a test: no branch of Decide may return an action weaker than one a later branch would have returned.
Landed

Fixed in chat/permissions.go. The Plan Mode test moved above the workspace-scope test, so the hard refusal is decided before the prompt. The doc comment states the general rule the ordering encodes: no branch may return an action weaker than one a later branch would have returned. Regression: TestPlanModeDeniesEvenOutsideTheWorkspace covers bash, write and edit aimed both inside and outside the workspace.

A-04criticalreadfixed

arac disable deletes any Claude Code hook whose command contains "arac"

internal/cli/disable.go:347 isAracneHookEntry, the test at :355

Requirements
The user runs arac disable, and their .claude/settings.json holds any other hook whose command string contains the four characters arac anywhere.
Effect

The ownership test is strings.Contains(cmd, "arac") on the raw command. It matches an unrelated hook that merely contains the substring — characterize.sh, barracuda-lint, ./scripts/paracelsus, a path under ~/aracnid/, or anything referencing a directory whose name happens to contain it. That entry is then removed from the user's settings file.

This is destructive to a file aracne does not own, in a command whose whole promise is that it cleanly removes only what arac setup added, and there is no backup and no diff shown.

Fix
Match what setup actually writes. The generated hooks are arac-guard.sh and arac-update-file.sh, both under the project's hooks directory, so the test can be exact: 
func isAracneHookEntry(entry interface{}) bool {
    …
    base := filepath.Base(firstWord(cmd))
    return base == "arac-guard.sh" || base == "arac-update-file.sh" ||
           strings.TrimSuffix(base, ".exe") == "arac"
}
Better still, have arac setup stamp a marker key on the entries it writes ("_aracne": true) and have disable remove exactly those — then ownership is recorded rather than guessed. Either way, print which entries are being removed before writing.
Landed

Fixed in cli/disable.go, cli/native_hooks.go. Ownership is decided by the command WORD and by the script names setup writes, never by a substring. isAracneHookEntry delegates to native_hooks.go's own predicates — so the writer and the remover cannot name different things — plus a command-word test for the legacy bare arac <subcommand> form older binaries installed, which arac disable still has to clean up. hookEntryCommandContains was itself too loose and became hookEntryRunsScript, which base-names the command word instead of scanning the whole string; every spelling in this repository's history is a bare script path, so all of them still match. Regression: a table case asserting characterize.sh, /opt/bin/barracuda-lint, ~/aracnid/run.sh and echo not-arac-guard.sh are all kept.

B-01highreproducedfixed

A legal tools/call with no arguments fails every tool

internal/mcp/server.go:131 handleCallTool · every Run implementation, e.g. llm/tools/warnings_list.go:41, bug_list.go:41

Requirements
An MCP client that omits the arguments member when a tool has no required parameters. warnings_list, bug_list and node_list_no_description all declare every parameter optional, so this is the natural call for them.
Effect

CallToolParams.Arguments is a json.RawMessage with omitempty. When the member is absent it stays nil, and every tool's first line is json.Unmarshal(args, &params), which on nil input returns unexpected end of JSON input. The call comes back as a tool error carrying a JSON parser message, which tells the model nothing about what it did wrong.

Claude Code sends "arguments": {} and never hits this, which is precisely why it has survived — it is a defect that shows up on the second host, the same class as the *int request ID the protocol comment already describes fixing for the same reason.

Evidence
{"method":"tools/call","params":{"name":"warnings_list"}}
  -> {"content":[{"text":"unexpected end of JSON input"}],"isError":true}

{"method":"tools/call","params":{"name":"warnings_list","arguments":null}}
  -> {"content":[{"text":"ok"}]}

An explicit null works, because a RawMessage then holds the four bytes null. Only the absent member fails.

Fix
Normalise once, at the one place that decodes the envelope, rather than in twenty Run methods: 
if len(call.Arguments) == 0 {
    call.Arguments = json.RawMessage("{}")
}
result, err := t.Run(call.Arguments)
handleCallTool also rejects a tools/call with no params at all for the same reason; guard that with len(params) > 0 before unmarshalling.
Landed

Fixed in mcp/server.go. An absent arguments member is normalised to {} at the one place that decodes the envelope, so every tool gets a valid payload — including tools added later. An absent params no longer reaches json.Unmarshal either, and a call with no tool name is reported as Invalid params rather than as whatever the JSON parser says about nil input. Regression: TestCallToolAcceptsOmittedArguments drives all three spellings (omitted, null, {}) through dispatch and asserts the tool was reached.

B-02highreproducedfixed

The chat workspace scope never inspects ids, so any absolute path reads

internal/chat/permissions.go:63 referencesOutsideWorkspace — keys checked are file_path, path, workdir, command · :118 isReadOnlyTool

Requirements
features.chat on, and read / read_resource in the chat agent's tool list — which is the default. read.kinds must include file, which is also the default.
Effect

The scope check looks at four argument names. The read tool's parameter is called ids, so nothing in a read is ever examined. isReadOnlyTool then classifies read and read_resource as read-only and returns allow with the reason "read-only in workspace" — a claim nothing verified.

An absolute path that is not a resource ID falls through unitFor to rawFileUnit, which reads the file off disk. So a chat session can read any file the process can read, without approval, in every approval mode. The comment above the command branch describes discovering this exact class of hole for bash; the read tool is the other half of it.

Evidence
read_resource {"ids":["/etc/passwd"]}
  -> allow (read-only in workspace)
Fix
Make the extractor cover list-valued arguments, and treat the read tool's ids as candidate paths: 
for _, key := range []string{"file_path", "path", "workdir", "ids"} {
    for _, v := range stringOrStringSlice(values[key]) {
        if looksLikePath(v) && !p.insideWorkspace(v) { return true, v }
    }
}
A resource ID such as internal/cli.RunGuard is not a path and must not be rejected, so gate on filepath.IsAbs or the presence of a separator, as toolspec.CommandPaths already does. The deeper fix is to enforce the workspace boundary inside rawFileUnit as well, so a bypass at the policy layer is not the only thing standing between a chat session and the filesystem.
Landed

Fixed in chat/permissions.go. The scope extractor now reads list-valued arguments and includes ids. Only absolute tokens among the ids are judged, which is the rule the command branch already applied, so resource ids like internal/cli.RunGuard and relative paths keep working. Regression: TestReadIDsOutsideWorkspaceAreNotAutoAllowed, with TestReadIDsInsideWorkspaceStayAllowed pinning that ordinary reads did not become scope questions.

B-03highreproducedfixed

descriptions apply writes LF comments into CRLF files

internal/helper/apply.go:81 split on "\n" · :100 rejoin with "\n"

Requirements
A source file with CRLF line endings — a Windows checkout, or any repository without * text=auto — containing at least one described resource, and a run of arac descriptions apply.
Effect

applyFile splits on bare "\n", so each existing line keeps its trailing \r and round-trips unharmed. The inserted lines come from renderLineComment / renderJSDoc / renderRustDoc, which produce no \r, and the rejoin uses "\n". The new doc comment therefore lands as a bare-LF line in a CRLF file.

The result is a file with mixed endings — noisy in a diff, and the exact whole-file-conflict outcome that matchLineEndings in llm/tools/edit.go was written to prevent, with a comment explaining why. The edit tool learned this lesson; the descriptions writer did not.

Evidence
after apply: CRLF lines=5  bare-LF lines=1
"package a\r\n\r\n// Does foo.\nfunc Foo() {\r\n\treturn\r\n}\r\n"
Fix
Detect the file's convention once and use it for both the split and the join, exactly as updateMarkdownIntegrationSegment already does with markdownLineEnding: 
eol := "\n"
if strings.Contains(string(data), "\r\n") { eol = "\r\n" }
lines := strings.Split(strings.ReplaceAll(string(data), "\r\n", "\n"), "\n")
…
return AtomicWriteFile(path, []byte(strings.Join(lines, eol)+trailer), 0644)
Handle B-04's trailer in the same change.
Landed

Fixed in helper/apply.go. applyFile detects the file's convention once, normalises to LF for the insertion pass, and rejoins with the ending the file actually had — so a doc comment written into a CRLF file arrives as a CRLF line. Stripping the carriage returns before the insertion pass also means the staleness and doc-block checks no longer see one inside a line. Regression: TestApply_PreservesCRLFLineEndings counts bare-LF lines in the result.

B-04highreproducedfixed

descriptions apply appends a trailing newline the file never had

internal/helper/apply.go:81–100 applyFile

Requirements
A described file whose last line has no terminating newline. Common in generated files, fixtures, and any corpus not written by an editor that adds one.
Effect

The read strips a trailing empty element (lines[len-1] == "") only when the file did end with a newline; the write unconditionally appends +"\n". So a file without a final newline gains one, in a run the user asked to insert doc comments.

Small in isolation, but descriptions apply is a sweep: it touches every described file in the project at once, and each such file gets a spurious one-line diff. In testing_ground/, where line numbers are asserted by roughly twenty test suites, an unintended trailing-newline change is the kind of edit CLAUDE.md warns about.

Evidence
before ends with newline: false
after  ends with newline: true
Fix
Remember whether the trailing newline was there and reproduce it: 
trailing := strings.HasSuffix(string(data), "\n")
…
out := strings.Join(lines, eol)
if trailing { out += eol }
return AtomicWriteFile(path, []byte(out), 0644)
Landed

Fixed in helper/apply.go. The same change records whether the file ended with a newline and reproduces that exactly, instead of appending one unconditionally. Regressions: TestApply_PreservesAMissingTrailingNewline and TestApply_PreservesASingleTrailingNewline pin both directions.

B-05highreproducedfixed

Deleting a language's last source file aborts the whole incremental scan

internal/helper/manifest.go:368 the refusal · topology/manager.go:143 if diffErr != nil { return nil, diffErr }

Requirements
A multi-language project where every source file of one language is removed or renamed — a Python helper script deleted, a single .rs prototype dropped, a lone .java file moved out — while at least one such file is still in the manifest.
Effect

DiffScanFiles has a guard against mass deletion: if the walk finds zero files of a language while the manifest holds some, it refuses and returns an error. The guard is sound as a guard, but IncrementalScan treats any diffErr as fatal and returns immediately — before processing the other languages' diffs.

So one deleted Python file wedges the incremental scan for the entire project. Every subsequent arac scan, every guard pre-tool scan and every drift check fails the same way, forever, because the manifest entry that triggers it is never removed. The graph silently stops tracking Go, TypeScript and Rust changes too, and the only recovery is a manual arac scan --all that nothing tells the user to run.

Evidence
added=[] modified=[] deleted=[]
err=no python source files found under root …;
     refusing to mark 1 manifest files deleted
Fix
Two changes, and both are worth making. Make the refusal per-language rather than fatal, so the other languages still scan: 
a, mod, d, diffErr := helper.DiffScanFiles(root, ls.Name(), manifestPath)
if diffErr != nil {
    topo.Errors["scan:"+ls.Name()] = diffErr.Error()
    continue   // this language is skipped, the rest are not
}
And make the guard distinguish "the tree really has none of these any more" from "the walk failed". Comparing against the previous scan's count, or requiring the root to be readable and non-empty, lets a genuine last-file deletion be processed instead of refused — otherwise the state stays unrecoverable by incremental scan by design.
Landed

Fixed in helper/manifest.go, topology/manager.go. Both halves, as the fix described. IncrementalScan records a failed language diff under a diff:<lang> key and continues, so one language no longer vetoes the others; the errors land in topo.Errors (cleared each scan, so one cannot outlive its cause) and the partial fast path is skipped while any is outstanding, since it has nowhere to record them. A scan where every diff failed still returns an error rather than reporting a quiet success. DiffScanFiles' guard now fires only while some manifest file is still on disk — a file the walk missed stats, a deleted one does not — so a genuine last-file deletion is processed. Regressions: TestOneLanguagesDiffFailureDoesNotVetoTheScan end to end (with the pyproject.toml that keeps Python detected after its last source file goes, which is what makes the wedge reachable), plus TestDiffScanFilesRefusesMassDeleteWhenFilesStillExist and TestDiffScanFilesReportsDeletionOfTheLastFileOfALanguage for the two sides of the guard.

B-06highreadfixed

The config is written non-atomically, and an unreadable config is replaced with defaults

internal/helper/config.go:1493 SaveConfig uses os.WriteFile · :1513 EnsureConfig overwrites on a parse failure

Requirements
A SaveConfig interrupted between truncate and write — Ctrl-C, a hook timeout that kills the process, an OOM kill, a full disk. Writers include arac init, arac setup, arac descriptions generate (which writes back the provider answers), and the viz PUT /api/config.
Effect

These two behaviours are individually defensible and jointly destructive. os.WriteFile truncates first, so an interruption leaves a zero-byte or half-written config.json. On the next run validConfig sees no known key, LoadConfigStrict reports false, and EnsureConfig — by design, and with a stderr notice — replaces the file with defaults. The project's mode, feature flags, ignore rules, agent tool lists and provider settings are gone.

The irony is documented: atomicwrite.go's own comment explains that WriteManifest was hardened after this repository's manifest was found empty, and that source files were next. The config is the one file where "empty" is not merely lost work but an automatic overwrite, and it is still on os.WriteFile.

Fix
Use the writer that already exists: 
func SaveConfig(cfg *Config, path string) error {
    …
    return AtomicWriteFile(path, buf.Bytes(), 0644)
}
Then consider making the clean break less absolute: before overwriting, move the unreadable file aside as config.json.bak and name it in the stderr notice. A user who lost a hand-tuned config can then get it back.
Landed

Fixed in helper/config.go. SaveConfig writes through AtomicWriteFile, so a reader never sees a truncated config and EnsureConfig is never handed one to replace with defaults. Regression: TestSaveConfigNeverLeavesATruncatedFile reads the file in a tight loop across 200 saves and fails if any read does not parse — it catches the old code immediately, on an empty file.

B-07highreadfixed

The post-write drift scan uses ".", not the topology root

internal/cli/guard_drift.go:116 mgr.IncrementalScan(".", reg) · contrast topology/manager.go:56 RunPreToolScan, which reads topo.Root

Requirements
The guard hook process runs with a working directory that is not the project root, and a PostToolUse Bash event that mayHaveWrittenSource accepts. guardDBPath explicitly supports this case — it resolves the database from the hook event's cwd, from $CLAUDE_PROJECT_DIR, or by walking upward from the process cwd — so the database can be found while "." is a subdirectory.
Effect

Three failures, in increasing severity. applyPathVisibility(".") builds the ignore matcher rooted at the subdirectory, so scan.ignore patterns resolve against the wrong base. reg.DetectAll(".") sees only the languages present below that directory, so the others are not diffed at all. And if it detects none, IncrementalScan returns no language scanner detected, which runGuardScan swallows — the drift backstop does nothing and says nothing.

The backstop exists because eight of twenty-seven benchmark agents wrote source through paths nobody had enumerated. It is the mechanism that turns an arms race into a converging one, and it stops converging the moment the model runs cd. guardDBPath's own doc comment records a whole benchmark cell lost to precisely this shape of bug.

Fix
Use the same root resolution the pre-tool scan uses. It is already available two ways: 
runGuardScan(dbPath, func(mgr *topology.TopologyManager, reg *scanner.Registry) (…) {
    return mgr.IncrementalScan(ProjectRootFor(dbPath), reg)
})
ProjectRootFor in guard_paths.go exists for exactly this and has no caller here. Better still, give TopologyManager a scanRoot() helper that prefers the stored topo.Root and falls back to the database's directory, and route both RunPreToolScan and driftCheck through it so they cannot drift apart again.
Landed

Fixed in cli/guard_drift.go. driftCheck scans ProjectRootFor(dbPath) — the helper that existed for this and had no caller — instead of a literal ".", matching what RunPreToolScan does on the way in. Regression: TestDriftCheckScansTheProjectRootFromASubdirectory scans a project, edits a file at its root, chdirs into a source-free subdirectory and asserts the new symbol was indexed; it fails on the old code.

C-01mediumreproduced

rg -r, ag -G and rg -y are read with GNU grep's meanings

internal/shellcmd/shellcmd.go:613 parseGrep · :661 the -r arm · :838 clusterable

Requirements
A search typed as rg, ag or ack using a short flag whose meaning differs from GNU grep's. The guard intercepts searches in every mode, so this is on by default for every project.
Effect

Long flags are correctly gated by tool family — includeFamily and typeFamily exist precisely so grep --glob and rg --include are refused. Short flags are not gated at all, and three of them mean different things:

rg -r is --replace and takes a value; the parser reads it as "recursive", consumes nothing, and the replacement text becomes the pattern while the real pattern becomes a path operand. ag -G is --file-search-regex and also takes a value; the parser reads it as the BRE dialect flag, so the file filter becomes the pattern. rg -y is not a ripgrep flag at all — real rg exits 2 with a usage error — and the parser accepts it as case-insensitive.

The package's opening comment is unambiguous that this is the failure it exists to prevent: "a flag this package does not model returns KindPassthrough… answering any of those would be a wrong answer wearing a helpful face." Most of the time the mis-shifted operand is not a real path, so arac cmd falls through and only a subprocess is wasted. When it is a real path — rg -r NEW old src/ with a file called old — a wrong search is answered confidently.

Evidence
rg -r REPLACEMENT pattern  =>  kind=grep pattern="REPLACEMENT" operands=["pattern"]
    (real rg: replace with REPLACEMENT, search for "pattern")

ag -G '\.go$' needle       =>  kind=grep pattern="\.go$"   operands=["needle"]
    (real ag: filter files by \.go$, search for "needle")

rg -y needle               =>  kind=grep ignorecase=true
    (real rg: exit 2, unrecognised flag)
Fix
Give short flags the same family gating the long ones have, keyed on the command word:
