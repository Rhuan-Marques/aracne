Aracne Under Opus

Aracne is being used, but only as a slower Read and a better grep. Opus adopts the three tools that mirror tools it already has — grep, read_file, edit — inside one or two turns, and uses them competently. It essentially never touches the topology: 15 node reads across 81 runs, zero read_struct, zero read_interface, zero warnings_list.

The +54% context bill is therefore being paid for a graph the model almost never queries. And the refusal is not stubbornness — it is correct on the merits. Sampling 120 real read_function calls across ten of these repos, 53% return no # CONTEXT: section at all, and on Python/JS the call returns the entire enclosing class (up to 88 KB for one method). A 50-line read_file cut is cheaper, never errors on a wrong ID, and loses nothing the model would have got.

The one genuine win is grep: 210 calls, well-narrowed, and 63% come back carrying resource IDs and descriptions the model could not have grepped for. That is the part of aracne that is beating the prior today.

The baseline arm is 97.5% Bash — one native Read call in 81 runs. Opus does its discovery with sed -n '660,770p' and grep -rn, not with the Read tool. Every comparison below is therefore aracne MCP tools vs. the shell, which is the harder and more honest baseline.

Q1

Is Opus understanding how to use aracne effectively?

Partly

It learns the surface fast and drives it competently. It never learns the graph. And it gets there by being blocked, not by being told.

The guard, not the contract, is doing the routing

Every one of the 81 aracne runs called ToolSearch to load the MCP schemas. But 66 of 81 runs (81%) opened with a Bash call — cat, ls, grep -rn — before touching aracne at all, and 71 of 81 runs (88%) hit at least one guard denial, 95 in total. The sequence is almost invariant:

The CLAUDE.md contract is present in context from turn zero and states plainly that native reads are blocked. The model reads it and tries cat anyway. That is a useful calibration: contract text does not change the first move; the denial does. The cost is roughly one wasted turn per run, before any work starts.

It self-selects only the tools that look like tools it already has

Because the MCP tools are deferred behind ToolSearch, the model must name the tools it wants. What it asks for is revealing:

The three tools with an obvious native counterpart are loaded in ~100% of runs. read_function is loaded in 58% — and then never called in 35 of those 47 runs. The model loads it out of diligence, looks at the task, and reaches for read_file instead.

The one structural handicap it can't work around

Across all 2,315 assistant messages in both arms, not a single one issued two tool calls in parallel. Batching happens only inside Bash — and there, the baseline is very good at it:

A single baseline turn does cat list.go && cat http.go, or sed -n 80,110p a.rs; sed -n 680,760p b.rs. Aracne's MCP tools take exactly one target per call, so the same work costs two or three turns — and every extra turn re-sends the whole accumulated conversation. That is the mechanism behind +25% turns and +54% context tokens, and no amount of prompt wording fixes it.

Is it using node reads instead of file reads?

No

The transition that never happens

Aracne's designed flow is grep to find the resource, then read the resource by ID. The grep output literally prints the ID above every match run. Here is what the model does with it:

Grep hands the model a resource ID and a description. The model takes the line number and goes back to the file. The intended grep → node-read transition fires 1% of the time.

Worth noting

When Opus does call a node read, it forms the ID correctly and idiomatically without being shown examples: Config.from_file, requests/utils.iter_slices, Flask.register_blueprint. Zero ambiguity errors across the whole arm. The forgiving-ID design works. The problem is not that the model can't address nodes — it's that it has no reason to.

Q3

What does a node read actually return?

Half the time, nothing extra

Transcripts store only result sizes, so I replayed the tools live against the frozen fixtures. Here is the exact wire format, and then the measurement of what it usually contains.

The shape, when it works

Descriptions reach the model as a flat # CONTEXT: block after the code fence — one ## <full-resource-id>: <description> line per neighbour, sorted, indented one level for members of a named type. This is read_function on ripgrep's ArgMatches::patterns, verbatim and complete:

That is the product working exactly as designed: the callee descriptions are genuinely useful, and they cost about 500 bytes. read_file on a whole file adds a second tier — the file's own members, nested under their enclosing type:

Note the duplication: every method description is emitted twice, once flat under ## and once indented under its struct. On this small file that is ~450 wasted bytes out of 780 of context.

The measurement: 53% of node reads carry no context at all

I sampled 12 random function/method resources from each of ten benchmark fixtures (two per language) and called read_function on each — 120 calls, zero errors.

The Python / JavaScript over-return

Defect

On Python and JavaScript, read_function on a method returns the entire enclosing class. Measured on these fixtures: Config.from_file → 14,273 bytes with a zero-byte context section, for a 20-line method. Session.__enter__ → 15,290 B. Blueprint.app_template_test → 20,743 B. Flask.test_request_context → 88,013 bytes, roughly 22k tokens, from one tool call.

In the same run, read_file("src/flask/config.py", 220, 290) returned 2,361 bytes and contained everything needed to make the fix. The model picked the 6× cheaper option. It was right.

Across the 27 benchmarked repos: 161,827 nodes, 68,161 described (42.1%), mean description length 130 characters (median 78) — roughly 20–30 tokens each. Coverage is extremely uneven, and it tracks which languages won:

Q4

Is it leaning on line-cut file reads? Why?

Yes — 69%, and rationally

212 of 306 read_file calls pass start_line/end_line. Median window: 50 lines. And a line-range read returns raw lines with no topology context, by design.

read_file by shape · 81 aracne runs
Shapecallsmean bytesmedian bytestotalTopology context
line range (start_line/end_line)212 (69%)2,2671,5780.48 MBnone — raw lines only
whole file94 (31%)7,0114,6300.66 MBfull # CONTEXT: block

Put plainly: 42% of every byte aracne returns through read_file arrives with zero topology value, because the model asked for a window.

Four reasons it prefers the line cut — three of them good

1. It is the native habit, transferred intact. In the baseline arm Opus issued 290 sed -n 'X,Yp' line-range reads. The same instinct simply routes through whatever tool is available. This is the training-prior component, and it is real.

2. The contract explicitly blesses it. The injected CLAUDE.md says, in the Navigation Model section the model reads first:

and the tool schema at benchmark time read "Read a file's source plus its topology context. Pass start_line/end_line for a raw line range instead." — neutral phrasing that presents the range as an equal option rather than a lossy one.

3. A line cut never misses. A node read can fail on an ID; a line range cannot. Nine read_* calls in this run came back as errors or near-empty results. The model has no way to know in advance which IDs resolve.

4. On Python and JS it is genuinely cheaper — often by 6×. Covered above. When read_function returns 14 KB of enclosing class with no context and a 70-line window returns 2.4 KB with the answer in it, preferring the window is not bias. It is arithmetic.

Already in flight

The working tree (uncommitted, post-benchmark) already sharpens both strings: the schema now reads "Prefer the whole file: a start_line/end_line range returns raw lines only, and walking a file in ranges costs a turn each", and claude_md.go has been rewritten to cut the contract roughly in half. Neither was in the binary these 162 runs used, so this report measures the old wording — the effect of the new wording is unmeasured and worth an A/B.

Q5

Is it using aracne's grep correctly? Is it searching by node?

Correctly — but there is no node to search by

Grep is the one part of aracne that is unambiguously working. 210 calls, 2.59 per run, and the narrowing options are used properly.

Only 3% of greps are unnarrowed sweeps. 87% carry at least one narrowing argument. This is skilled use.

How often the topology annotation actually fires

I replayed 142 of the real grep calls against their own fixtures. 90 (64%) came back with at least one # resource header; 88 (63%) with at least one description. Median 3 headers per annotated call; median result 1,282 bytes. Seven calls (5%) matched nothing.

That is real information ripgrep-the-tool cannot produce, delivered for about 90 bytes per resource. It is also why 13% of post-grep transitions go straight to edit — the grep answered the question.

But: the graph is output-only

Design gap

mcp__aracne__grep takes pattern, path, glob, type, case_insensitive, output_mode, head_limit, before, after. Every one of those is a ripgrep argument. There is no way to phrase a query in terms of the topology — no "resources whose description matches X", no "callers of Y", no "implementations of Z", no "restrict to functions". The graph appears only as decoration on results the model could have obtained with grep -rn.

So the answer to "is it searching by nodes" is: it can't. Neither can anything else in the MCP surface. That is the single largest missing capability in the product, and it is why read_function has no job to do — every question the model has can be answered with grep plus a line window, so that is what it does.

Q6

Can aracne beat the training prior, or is that hopeless?

Beatable — but not by prompting

The prior is real and visible. It is also not what is losing here, and this run contains the proof.

Opus adopted mcp__aracne__grep in 79 of 81 runs and mcp__aracne__edit in 81 of 81 — within one or two turns, with correct arguments, and it kept using them. If the prior were decisive, that would not have happened. What those two tools have in common is that they are drop-in: same mental model, same arguments, strictly more output for the same call. The model switched instantly and without persuasion.

The node reads are not drop-in. They ask the model to give up something it has (an addressing scheme that never fails, and shell batching) in exchange for something that, measured across 120 real calls, is absent 53% of the time and occasionally costs 22k tokens. Re-wording the contract cannot change that trade; only changing the payoff can.

The shape of the fix

Make the topology tool answer questions grep and a line-window cannot answer at all — reverse edges (who calls this, who implements this), batched neighbourhoods (one call, N resources), description-space search. Then the choice stops being "which read is cheaper" and becomes "there is no other way to get this." That is how grep already won.

The flask failure is an index bug, not a model failure

Reproducible defect

In all three aracne seeds, the very first read_function {"name": "Config.from_file"} returned is_error: true, 48 bytes — a "not found in topology" on a resource that plainly exists in the source and resolves fine when queried today. In seed 2 the transcript shows the recovery: after three mcp__aracne__edit calls forced a re-parse of config.py, the identical call succeeded and returned 14,273 bytes.

So the frozen fixture's topology.db was missing the node until a write repaired it. The model did the right thing, got a hard error on its first topology query, and fell back to read_file — where it produced a patch functionally identical to the baseline's (see the caveat below on why it was graded as a failure anyway).

What to change

Ranked by expected effect on the two numbers that matter — context tokens and node-read adoption. Every one is checkable by re-running this same matrix.

  1. Make reads batchable

    Accept a list: read_file{names:[…]}, read_function{names:[…]}, or one read{ids:[…]}. The baseline gets 1.64 discovery operations per turn out of the shell; aracne gets exactly 1.00, and no assistant message in 2,315 issued parallel tool calls. This gap is the direct cause of +25% turns, and turns are the cause of +54% context.

    effort: smallexpected: largest single win

  2. Stop returning the enclosing class from read_function

    On Python and JavaScript a method read returns the whole class body — 14 KB for Config.from_file, 88 KB for Flask.test_request_context. Return the method plus a one-line class signature, the way the Rust formatter already does. Until this is fixed, preferring a line window is the correct play and the model will keep making it.

    effort: smalllanguages: python, javascript, typescript

  3. Put the graph in the input, not just the output

    Add the queries that have no grep equivalent: callers_of(id), implementations_of(id), neighbors(id, depth), and a description-space search. Right now every question the model has can be answered with a regex and a line window, so it uses a regex and a line window. This is the capability that would make a node read the only way to get an answer.

    effort: mediumexpected: unlocks node-read adoption

  4. Annotate line-range reads instead of stripping them

    69% of read calls pass a line range, and they currently receive nothing but raw bytes — 42% of all read_file output. Naming the resources that overlap the requested span, with their descriptions, costs ~90 bytes per resource and would put topology in front of the model on its most common action rather than its rarest.

    effort: smallreaches: 212 of 306 read calls

  5. Give grep a resource-shaped output mode

    output_mode: "resources" returning id + kind + description + span, no source lines. Grep is already the entry point the model trusts, and 63% of calls already resolve resources. Handing back IDs plus a batched read (rec. 1) is a genuine token win over grep -rn plus sed, and it creates the grep → node-read transition that currently fires 1% of the time.

    effort: smallpairs with: 1, 3

  6. Fix the cold-index miss and surface index health

    Config.from_file was unresolvable in a frozen fixture until an edit forced a re-parse — it cost that instance 3 of 3 runs. Whatever leaves a restored DB incomplete needs finding, and a miss should say "not indexed" rather than "not found" so the model (and the benchmark) can tell a bad ID from a stale database.

    effort: mediumcorrectness

  7. Collapse the three node readers into one

    read_interface was requested 0 times in 81 runs and read_struct 4 times. Splitting by kind forces the model to know a resource's kind before it can read it, which is exactly the thing it is asking. One read_node{id} that dispatches internally removes a decision and shrinks the deferred-tool surface the model has to discover.

    effort: smallsimplification

  8. De-duplicate the # CONTEXT: block

    Whole-file reads print each member description twice — once flat under ##, once indented under its type. On logger.rs that is 450 of 780 context bytes. Free savings on the read shape that does carry topology.

    effort: trivial

  9. Re-measure the contract rewrite on its own

    The uncommitted claude_md.go rewrite and the sharpened read_file schema both target exactly the behaviour this report measures, and neither was in the benchmarked binary. Run them as a standalone A/B before bundling them with the tool changes, or the two effects will be impossible to separate.

    effort: one runmethodology

  10. Fix per-seed grading before trusting any correctness delta

    See the caveat below — seed outcomes in this run are not independent. The efficiency numbers are per-run and unaffected, but the ±3.7pp solve-rate difference should not be quoted until this is corrected.

    effort: smallblocks: correctness claims

Method & caveats

What was analysed

All 162 transcripts and all 162 telemetry rows in bench/results/opus-medium-seeds3/ — every tool call, every argument, every result size, in both arms. That part is a census, not a sample.

Tool result bodies are discarded at capture time (bench/bench/toolstats.py replaces each with <N bytes elided>), so byte counts survive but content does not. To recover content I ran arac serve over stdio JSON-RPC directly against the frozen fixture worktrees and replayed calls: 120 sampled read_function calls across 10 repos (2 per language) for the output-composition table, and 142 of the benchmark's own real grep calls for the annotation rate. Every verbatim exhibit in this report is a live capture, not a reconstruction.

Caveat 1 — seed outcomes are not independent

The predictions file writes three rows per instance (one per seed) all sharing instance_id and model_name_or_path. SWE-bench keys its report at logs/run_evaluation/<run>/<model>/<instance_id>/report.json — one report per instance — and grade.py then assigns row["success"] = resolved[task.key] to every seed row of that instance. All three seeds receive one grade, taken from whichever patch the harness graded.

The signature is visible in the data: across 54 instance×arm cells, every single one is 0/3 or 3/3 — never 1/3 or 2/3. And the patches genuinely differ: flask seeds 0 and 1 produced a patch functionally identical to the passing baseline, while seed 2 used a different parameter name and genuinely fails. All three were recorded as failures.

Consequence: effective N for correctness is 27 instances with one graded patch each, not 81 runs. Everything in this report about behaviour and efficiency is measured per run and is unaffected.

Caveat 2 — the binary is one commit behind the tree

These runs used bin/arac as built on 2026-08-26. The working tree carries uncommitted changes to universal_read.go, grep.go, warnings_list.go and a substantial rewrite of claude_md.go. Where those changes bear on a finding, it is flagged inline.

Caveat 3 — the baseline is the shell, not the Read tool

Opus used the native Read tool once in 81 baseline runs. The comparison is against sed, cat and grep -rn inside Bash, which batch freely. This makes the baseline stronger than a Read-tool baseline would be, and it is the correct comparison — but it means the +25% turn penalty is partly a property of MCP, not of aracne specifically.

Caveat 4 — small per-language subsamples

27 instances across 5 languages: python 8, rust 8, javascript 5, go 3, typescript 3. Per-language claims (including the TypeScript win and the JavaScript regression) rest on 3–8 repos and should be treated as directional.
