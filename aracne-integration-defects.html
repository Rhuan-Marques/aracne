Aracne Harness Defect Register

Twenty-one defects in the code paths that carry aracne into Claude Code and OpenCode — the guard hook, the shell classifier, arac cmd, the generated integration files, and the index-health primitive they all consult.

suite go test ./... — all pass
method read + reproduced against a live binary

What this is

Every entry below was reached by reading the code and then reproducing the behaviour with a freshly built arac against purpose-built fixtures (a single-language Go project, a Go+Python project, a 25,000-file project) and, where it was safe to do so, against this repository itself. Nothing here is inferred from a comment; where a comment and the code disagree, the finding says which one is wrong.

The bar for inclusion was: this is not a design decision, and I can show it. Behaviour that is deliberate and documented — the tiered grep ranking, the elision markers, passthrough for unmodelled flags, the terminal.max_overserve ceiling as a concept — is not listed as a defect even where it surprises. Twenty of the twenty-one carry a reproduction transcript; the one that does not (F18) is a timing race whose mechanism is unambiguous in the code but which I could not land in a controlled test, and it says so.

The whole test suite passes, including -tags minimal. None of these are caught by it. Five are asserted by the dormant -tags audit suite, which does not compile in two packages and is not run by make test — noted per finding.

F01 Critical Reproduced

Every multi-language repository reports as permanently stale, and no scan can clear it

internal/topology/indexhealth.go:35 detectedLanguages · internal/helper/manifest.go:236 IsSourceFile

Trigger

Any project whose topology holds more than one language — i.e. info.language == "multi" — that also contains Go test files (*_test.go) or Python test files (test_*.py). Aracne's own repository is in this state right now.

Mechanism

detectedLanguages unions the stored topo.Languages, the stored topo.Language, and Registry.DetectAll. For a multi-language project topo.Language is the aggregate sentinel "multi", which is not a scanner name. IndexHealth then calls DiffScanFiles(root, "multi", …), and IsSourceFile has no case "multi" — it falls into default:, which accepts any .go or .py file without the per-language test-file exclusions that the real case "go" and case "python" arms apply.

The scanners never index those files, so they are never stamped into the manifest, so the diff reports them as added on every single run, forever. The watch loop (cli/scanner.go) and IncrementalScan both enumerate through Registry.DetectAll and use real scanner names, so they are unaffected — which is exactly why the two disagree permanently.

Effect

  • arac check-updates always exits 1 and prints “The topology is STALE for these files. Run arac scan to re-index” — advice that can never work. On this repository: 192 phantom files.
  • Read.indexHealthNote (universaltools/read.go:621) appends “NOTE: the index is STALE — 192 file(s) out of sync” to every unresolved read. A model that mistypes an ID is told the database is broken. This makes the one signal that distinguishes “wrong ID” from “not indexed” permanently useless.
  • driftCheck gates its scan on indexHasDrifted, which returns health.Stale(). It is permanently true, so the guard runs a full IncrementalScan (a whole-tree manifest walk) after every unclassified Bash command — ls, go build, npm test, git status. That is precisely the cost the comment at guard_drift.go:156 says the probe was added to avoid.

Reproduction

# a two-language fixture: main.go + main_test.go + mod.py + test_mod.py
$ arac scan && arac check-updates
2 file(s) not up to date:
  Added (2):
    + main_test.go
    + test_mod.py
The topology is STALE for these files. Run `arac scan` to re-index.
$ arac scan && arac check-updates      # identical output, forever
$ arac read NoSuchThing
# UNRESOLVED:
- NoSuchThing: resource "NoSuchThing" not found in topology
NOTE: the index is STALE — 2 file(s) out of sync (2 new) …

# the single-language control is clean:
$ cd ../go-only && arac check-updates
All files are up to date.

# and on this repository:
$ arac check-updates | head -1
192 file(s) not up to date:

Fix

Two independent guards, both cheap:

  1. In detectedLanguages, do not add the aggregate sentinel. add(topo.Language) exists for the single-language case where Languages is empty; gate it — if len(topo.Languages) == 0 { add(topo.Language) } — or skip the literal "multi" explicitly. That alone fixes all three symptoms.
  2. Harden IsSourceFile's default: branch so an unrecognised language name still applies the per-language test exclusions it composes: !strings.HasSuffix(name, "_test.go") for .go, !strings.HasPrefix(name, "test_") for .py. The JS/TS/Rust/Java arms already delegate to helpers that carry their own exclusions, so only these two are missing.

Regression test: scan a Go+Python fixture with test files in both, assert IndexHealth.Stale() is false immediately after a scan. internal/topology/indexhealth_test.go exists and is untracked — this is the case it is missing.

F02 Critical Reproduced

`arac setup` silently deletes a project's own “# Aracne” section

internal/cli/setup.go:747 findAracIntegrationStart · :764 aracIntegrationBounds · :784 writeMarkdownIntegrationFile

Trigger

A CLAUDE.md or AGENTS.md that already contains a top-level heading whose text is exactly # Aracne — the obvious heading for a team documenting its own aracne conventions — anywhere above the generated block, or with no generated block at all.

Mechanism

findAracIntegrationStart takes the first line in the document equal to # Aracne. findAracIntegrationEnd then searches forward from there for a closing marker; when the user's section has none, aracIntegrationBounds falls back to nextTopLevelHeading. Everything between the user's heading and the next # heading — or, when a real aracne block follows, everything up to its closing line — is replaced wholesale. writeMarkdownIntegrationFile never prompts and writes atomically, so the only trace is in git.

Effect

Silent, unrecoverable-outside-VCS loss of hand-written agent instructions in the one file a team is most likely to have hand-written agent instructions in. It compounds: the file is rewritten on every arac setup, and arac init calls runSetup itself.

The risk is not hypothetical for this project. Aracne's own CLAUDE.md devotes a section to explaining the injected block; a single line spelled # Aracne in that prose would be eaten by the next arac setup.

Reproduction

$ cat CLAUDE.md
# My Project

Some notes.

# Aracne

We use aracne here. See docs/aracne.md for our house rules.
IMPORTANT: never run `arac scan --hard`.

# Build

Run `make build`.

$ arac setup -y --claude
Claude Code CLAUDE.md updated at CLAUDE.md

$ grep -c "house rules" CLAUDE.md
0        # both sentences gone; the generated contract sits in their place

Content after a well-formed block, and re-runs over a block aracne itself wrote, are correctly preserved — I verified both. The failure is specific to a foreign # Aracne heading.

Fix

The block needs an identity the parser can verify, not just an opening heading it can find. Three options, in increasing order of robustness:

  • Minimal. Require the heading to be followed by the contract's own first line (`.aracne/topology.db` holds a pre-analyzed graph… / the cli variant) before treating it as aracne's. Costs nothing in the prompt and rejects a foreign heading immediately.
  • Better. Only accept the fallback-to-nextTopLevelHeading path when an aracne-authored block was previously recorded — persist the block's hash in .aracne/ at write time and refuse to replace anything that does not match.
  • Belt. When bounds are resolved by fallback rather than by a closing marker, print what will be removed and require -y to proceed. writeMarkdownIntegrationFile's no-prompt rule is right for a file aracne owns; this file it does not own.

The argument in the code for not using an HTML comment delimiter (it would be noise the model can see but not use) is sound and none of these options reintroduce one.

F03 High Reproduced

OpenCode installs no post-tool hook, so a topology warning never reaches the model

internal/cli/setup.go:149-153 initOpenCode · internal/cli/native_hooks.go:449 writeOpenCodePreToolScanPlugin · internal/cli/plugins.go:48 writeOpenCodePlugins

Trigger

Any OpenCode project with a default config, in any mode. llm.opencode.main_agent.plugins is empty in DefaultConfig(), and arac init never asks about it.

Mechanism

arac setup installs exactly one plugin unconditionally for OpenCode: arac-pre-tool-scan.js, which registers only tool.execute.before. The tool.execute.after handler lives in arac-native-edit-sync.js, which is written only when the agent lists edit-update-db-plugin in plugins — and no shipped path sets that. The Claude Code side has no equivalent gap: its guard hook is registered for both PreToolUse and PostToolUse, and driftCheck hangs off the latter.

Effect

The generated AGENTS.md ends with “Edits keep the graph current automatically; act on any topology warning that comes back.” On OpenCode nothing ever comes back. Concretely, on a default install:

  • A native edit that breaks eleven callers produces zero visible warnings.
  • A shell write that breaks a caller produces zero visible warnings.
  • The drift backstop for unclassified commands — the whole reason driftCheckApplies exists — never runs.
  • Outside mcp mode the main agent has no warnings_list tool either, so the only surviving route is a human typing arac warnings list.

Warnings are the one capability docs/architecture.md §9 describes as having no substitute. On one of the two shipped harnesses the channel is dead by default.

Reproduction

$ arac setup -y            # default config, mode: cli
[OpenCode] Config written to .opencode/opencode.json
OpenCode pre-tool scan plugin written to .opencode/plugins/arac-pre-tool-scan.js

$ ls .opencode/plugins/
arac-pre-tool-scan.js

$ grep -c "tool.execute.after" .opencode/plugins/*.js
0

$ grep "topology warning" AGENTS.md
Edits keep the graph current automatically; act on any topology warning that comes back.

Fix

Add a tool.execute.after handler to arac-pre-tool-scan.js — the plugin that is already installed unconditionally — mirroring what the Claude guard's PostToolUse arm does. It needs a CLI entry point that does the same job without a hook event; arac guard --rewrite and --pre-scan already set the precedent, so add arac guard --post-tool <tool> (or reuse --drift) that runs driftCheckApplies-equivalent logic and prints the ledger delta from unreportedWarnings. The plugin appends whatever comes back to output.output, exactly as arac-native-edit-sync.js already does for its own messages.

Doing it in the always-installed plugin rather than promoting the edit-sync one is the right split: the edit-sync plugin is an optimisation (it syncs inline), while the warning report must not be optional. Both already go through guard-reported-warnings.json, so whichever runs first reports and the other adds nothing.

Separately: either make edit-update-db-plugin reachable (ask in arac init, or default it on) or drop it — a plugin flag no shipped path can set is dead configuration surface, and guard.go:339 already documents the fallout.

F04 High Reproduced

A read with a stderr redirect is classified as an edit — and refused as one

internal/cli/guard.go:729-734 (the '>' arm of splitCommandSegments) · internal/toolspec/toolspec.go:382 ShellCommandKeyForArgs · internal/cli/guard_intercept.go:113

Trigger

Any sed -n or awk read carrying a stderr redirect — 2>/dev/null, 2>err.log — which is a completely ordinary thing for an agent to write. Denial requires blocked_tools to contain edit in mcp or cli mode; the interception and scan effects apply in every mode with no configuration at all.

Mechanism

The scanner's '>' arm sets curRedirect = true for any > that is not followed by &. It has no notion of a file-descriptor prefix, so 2> — which redirects stderr — sets the same flag as >, which redirects stdout. redirectsOut then feeds two places that both read it as “this command writes a file”:

  • ShellCommandKeyForArgs: case streamEditors[name]: if redirectsOut || streamEditorMutates(…) { return "edit", true }.
  • interceptableSegment: if seg.pipedInto || seg.redirectsOut { return … false }.

Effect

  • A pure read is denied under blocked_tools: ["edit"], with guidance telling the model to pipe JSON into arac edit to “apply several replacements”. That is a confidently wrong refusal of the exact kind the guard's own doc comments say the design exists to prevent.
  • Interception is refused for every command carrying 2>/dev/null, reads and searches alike — so a very common idiom quietly opts out of the whole product.
  • mayHaveWrittenSource sees edit and runs a post-tool incremental scan after a command that wrote nothing.

Reproduction

# mode: cli, blocked_tools: ["edit","write"]

$ echo '{"hook_event_name":"PreToolUse","tool_name":"Bash",
         "tool_input":{"command":"sed -n 1,5p main.go"},"cwd":"…"}' | arac guard --claude-hook
                                        # (silence — correctly allowed)

$ echo '{"hook_event_name":"PreToolUse","tool_name":"Bash",
         "tool_input":{"command":"sed -n 1,5p main.go 2>/dev/null"},"cwd":"…"}' | arac guard --claude-hook
{"hookSpecificOutput":{"permissionDecision":"deny","permissionDecisionReason":
 "Blocked by aracne config (blocked_tools: edit). aracne: `echo '{\"edits\":[…]}' | arac edit`
  applies several replacements in ONE call…"}}

# same for awk; and interception is refused outright in every mode:
$ arac guard --rewrite "grep -rn needle . 2>/dev/null"
{}
$ arac guard --rewrite "grep -rn needle ."
{"command":"…/arac cmd -- grep -rn needle ."}

Fix

Teach the scanner the descriptor prefix. In the '>' arm, only set curRedirect when the redirect targets stdout: it does not when the immediately preceding non-space rune of the current token is a digit other than 1. Concretely, look back over the accumulated token for a trailing [0-9]; if present and not 1, this is a non-stdout redirect and the flag stays clear. &> (both streams) should still set it, and 2>&1 is already excluded by the existing & check.

The look-back must be at the raw runes rather than the accumulated segment text, for the same reason isRedirectAmpersand (guard.go:742) already does it that way — quote characters have been dropped by then.

Table-test it beside the existing redirect cases: sed -n '1,5p' f 2>/dev/null → read; sed -n '1,5p' f > out → edit; sed -n '1,5p' f &> out → edit; sed -n '1,5p' f 2>&1 → read.

F05 High Reproduced

An over-budget resource-ID read falls through to `cat`, which reports that the ID does not exist

internal/cli/cmd.go:213 serveRead · :597 passthrough · internal/helper/overserve.go:24 OverserveMaxBytes

Trigger

intercept_id or intercept_line_ranges mode; a cat/head/tail/sed -n whose operand is a resource ID (not a path) that renders to more than 32 KB. OverserveMaxBytes is an absolute ceiling applied after the ratio, so it is reachable however generous terminal.max_overserve is.

Mechanism

serveRead returns ok=false when the answer exceeds the budget, and RunCmd answers ok=false by running the command the caller typed. For a path that is exactly right. For an ID the shell then runs cat <id> and prints “No such file or directory.”

The doc comment on rawWindowBytes (cmd.go:557) names this outcome as the bug it was written to fix — and it did fix the denominator (a resource ID used to score as zero bytes). The absolute cap re-opens the same door on the numerator side, and nothing downstream distinguishes “over budget” from “not a file”.

Effect

The intercept_id contract teaches cat <resource-id> in a fenced example. For any declaration large enough to matter — the ones a model most wants to read whole — that command answers with a false claim that the ID does not exist. The recovery a model picks from “No such file or directory” is “I got the ID wrong”, which is an exploration turn spent on nothing.

Reproduction

# a single 124-line function whose source is 58 KB, mode: intercept_id
$ arac cmd -- cat 'example.com/demo.Wide'; echo "exit=$?"
cat: example.com/demo.Wide: No such file or directory
exit=1

$ arac read 'example.com/demo.Wide' | head -2
```wide.go
func Wide() {           # the same ID resolves perfectly well

Also asserted by the dormant TestAudit_OverBudgetResourceIDIsRefusedNotPassedThrough (internal/cli/audit_test.go, -tags audit), which currently fails.

Fix

Make “over budget” a different answer from “nothing to add”, and only for an operand the shell cannot serve. serveCommand already has the right channel: the third return, refusal, which RunCmd prints to stderr and exits 1 on rather than passing through — added for exactly this class of operand (the read.kinds refusal).

In serveRead, thread through whether any operand resolved as an ID rather than a path (resolveReadOperand already knows). When the budget check fails:

  • all operands were paths → return ok=false as today; the real command is a correct answer;
  • any operand was an ID → return a refusal naming the size and the cheaper move, e.g. “example.com/demo.Wide renders to 58 KB, over the 32 KB ceiling; read a range of it (sed -n '3,127p' wide.go) or raise terminal.max_overserve.”

An alternative worth considering alongside it: for an ID over budget, fall back to the skeleton rendering rather than refusing — it is the same declaration, abridged, and already exists (skeletonBody).

F06 High Reproduced

Intercepted searches silently drop matches a real grep finds — including in `--piped` mode

internal/topogrep/grep.go:963 prunedDirs · :1003 wantFile · Options.Plain doc, grep.go:196-216

Trigger

Any search whose matches live under node_modules, vendor, .venv, venv, .tox, .next, .nuxt, .gradle, .terraform, the various caches — or under any scan.ignore glob. Searches are intercepted in every mode, so this needs no configuration.

Mechanism

walkOneRoot prunes prunedDirs and applies opt.Ignore, and serveGrep builds that matcher from scan.ignore. Neither is disabled under Plain. For the enriched surface that is a defensible editorial choice; for Plain it directly contradicts the invariant Options.Plain's own documentation states — “What it delivers is the same SET of rows, each byte-identical, in path and line order.”

Plain is what the guard splices in when a search feeds a pipeline whose every stage preserves lines. The whole safety argument for that splice is that the rows are the ones the real command would have printed.

Effect

  • grep -rn X . | grep -v test | head -30 is rewritten and returns a strictly smaller set than the real pipeline, with nothing to mark the substitution. This is the same failure class as the | wc -l case ConsumerPreservesLines was written to refuse, arriving through the filter it lets through.
  • On the enriched surface a model searching a JS repo for an imported symbol gets zero hits from node_modules and may reasonably conclude the dependency is unused; same for a Go repo with a vendor/ tree.
  • No trailer says anything was skipped. The truncation trailer exists and is well-designed; this omission has no counterpart.

Reproduction

$ /usr/bin/grep -rn needle .
./node_modules/dep.js:1:const needle = 1;
./vendorlike/x.txt:1:needle

$ arac cmd --piped -- grep -rn needle .
./vendorlike/x.txt:1:needle          # the node_modules hit is gone, exit 0

$ arac guard --rewrite 'grep -rn needle . | grep -v x | head -3'
{"command":"…/arac cmd --piped -- grep -rn needle . | grep -v x | head -3"}

Fix

Split the two cases, because they want opposite answers:

  • Plain: honour the promise. Skip prunedDirs and opt.Ignore entirely when opt.Plain is set — a pipeline reading the output has no way to notice an omission, and the rows must be the real command's rows. That is the same reasoning effectiveLimit already applies to the head limit under Plain (grep.go:857).
  • Enriched: keep the pruning, but say so. When the walk skipped a directory that would have been searched, append one line to the trailer: “… skipped node_modules, vendor (aracne never searches these; --no-ignore or a path operand reaches them).” A directory named outright as an operand is already exempt — walkOneRoot searches a named file whatever the filters say — so the escape hatch exists; the model just cannot see it.

If skipping the prune list under Plain is judged too expensive on a large node_modules, the honest alternative is to refuse the splice entirely when the walk would prune anything under the requested roots, and let the real command run.

F07 Medium Reproduced

`blocked_tools: ["grep"]` in `cli` mode: OpenCode refuses what Claude Code answers

internal/cli/setup.go:105-111 initOpenCode · compare internal/cli/guard.go:509 loadGuardConfig · internal/helper/config.go:1354 BlockableInMode

Trigger

mode: "cli" (the default) with grep in blocked_tools — which BlockableInMode's own doc calls “a reasonable thing to write when moving a project between modes”.

Mechanism

initOpenCode gates the blocked set on cfg.GuardBlocksNativeReads() but then takes the operator's list raw: blocked = toolNameSet(mainEff.BlockedTools). The Claude Code guard takes the same list through cfg.BlockableInMode(...), which drops grep outside mcp mode — because search is intercepted in every mode and refusing it would deny a command aracne was one step from answering.

So the OpenCode permission block enforces a policy the guard is explicitly written not to enforce. The comment immediately above the offending line says: “Denying a native read here in a mode whose guard would never deny it is how the two enforcement paths drift apart.”

Effect

The same project behaves differently on the two harnesses, and the documentation of it is wrong on both. contractGuardNote correctly applies BlockableInMode, so the generated AGENTS.md says nothing about a grep restriction that OpenCode will actually apply — the model is refused with no explanation, which is the exact failure that note exists to prevent.

Reproduction

# .aracne/config.json: mode "cli", blocked_tools ["grep"] on both harnesses
$ arac setup -y

$ jq .permission .opencode/opencode.json
{ "read": "allow", "edit": "allow",
  "bash": { "*": "allow", "grep *": "deny", "rg *": "deny" },
  "aracne_*": "deny" }

$ arac guard --rewrite 'grep -rn needle .'
{"command":"…/arac cmd -- grep -rn needle ."}     # Claude Code answers it

$ grep -i "tool guard" AGENTS.md
                                                  # nothing: the contract says no restriction exists

Fix

One line. In initOpenCode, replace

blocked = toolNameSet(mainEff.BlockedTools)

with

blocked = cfg.BlockableInMode(toolNameSet(mainEff.BlockedTools))

and drop the surrounding if cfg.GuardBlocksNativeReads(), which BlockableInMode already performs (it returns an empty map when the mode may not block). That leaves exactly one definition of “what may this mode refuse”, which is what BlockableInMode's doc claims it is.

Then pin it: a test that, for each of the four modes × each blockable tool, asserts the OpenCode permission map and the Claude guard's loadGuardConfig agree. internal/cli/guard_opencode_test.go is untracked and is the natural home.

F08 Medium Reproduced

Three config enums have validation that can never fire

internal/helper/config.go:1432 normalizeConfig · :744 Validate · :1261/:1281 EffectiveMode / EffectiveContractVerbosity

Trigger

A typo in mode, contract_verbosity, or read.context_filter.

Mechanism

LoadConfigRead calls normalizeConfig, which stamps the coerced value back onto the struct: c.Mode = c.EffectiveMode(), and the same for ContractVerbosity and the context filter. Every Validate() call site loads through that path, so by the time the switch runs, the unknown value has already become a known one. EffectiveMode's doc comment promises the opposite: “Validate() is where a typo is reported, loudly and once.”

Effect

"mode": "intercept_lineranges" (a plausible misspelling of intercept_line_ranges) silently resolves to cli. The project loses read interception entirely, the generated contract stops promising it, and the config file on disk still says intercept_lineranges — so the operator reads the file, sees what they intended, and has no way to reconcile it with the behaviour. announceMode prints “Mode: cli”, which is the only hint, and it does not read as an error.

The neighbouring validations — read.kinds, scan.pre_tool, mcp_tools, blocked_tools — all work correctly; these three are the ones normalisation reaches first.

Reproduction

$ echo '{"mode":"intercept_lineranges"}' > .aracne/config.json
$ arac setup -y | head -1
Mode: cli — no MCP tools; the contract points at `arac read ` for symbols.
$ jq -r .mode .aracne/config.json
intercept_lineranges

$ echo '{"contract_verbosity":"hgih"}'      > .aracne/config.json && arac setup -y   # accepted
$ echo '{"read":{"context_filter":"ful"}}'  > .aracne/config.json && arac setup -y   # accepted
$ echo '{"read":{"kinds":["fnction"]}}'     > .aracne/config.json && arac setup -y
Invalid .aracne/config.json: read.kinds: unknown read.kinds value(s): fnction     # this one works

Fix

Validate the raw text, not the normalised struct. Keep the raw value alongside the resolved one — the cleanest shape is for LoadConfigRead to run validation on the decoded struct before calling normalizeConfig, and to carry the result. Since Validate() is a method callers invoke separately, the minimal change is:

  • have normalizeConfig record the pre-coercion spellings on unexported fields (rawMode, rawVerbosity, rawContextFilter);
  • have Validate() switch on those when set, falling back to the public field for a hand-constructed Config.

The fail-soft behaviour of EffectiveMode should stay exactly as it is — a config aracne cannot read must never leave a project with no surface. The point is that the surface that can report it should.

Also worth a line in announceMode: when the raw value differs from the resolved one, print “(mode "intercept_lineranges" is not recognised; using cli)”. Even after the validation fix, that is the message someone running arac setup in a script will actually see.

F09 Medium Reproduced

`cat f.go` returns less than `head -40 f.go` on the same 38-line file

internal/cli/cmd.go:230 renderReadOperand · internal/helper/config.go:584 EffectiveFileMode · contract text at internal/prompts/contract.go:150

Trigger

Either intercepting mode (where read.file_mode defaults to skeleton), a file holding a declaration longer than read.skeleton_threshold (12 lines), and a cat with no window.

Mechanism

renderReadOperand branches on the window: WholeFile goes through ReadIDs, which applies read.file_mode; every other window goes through ReadSlice, which does not. So the abridgement is a property of how the model spelled the request, not of the bytes requested. head -40 and sed -n '1,1000p' on a 38-line file are the same request as cat, and return more.

Effect

The intercepting contract says: “Read files the way you normally would — cat, head -40, sed -n '80,120p'. … the answer comes back enriched: the lines you asked for …”. For cat it is not the lines asked for; it is fewer. A model that notices will learn to type head -9999 instead of cat — a worse habit than the one skeleton mode exists to discourage — and one that has already been observed to be the model's instinct for windowed reading.

The elision marker is unambiguous and names the range, so nothing is silently wrong; the defect is the inconsistency and the contract sentence that does not survive it.

Reproduction

# big.go: 38 lines, one 32-line func Big() and one small func Small()
$ wc -l big.go
38 big.go

$ arac cmd -- cat big.go
```big.go
package main

// Big does a lot.
func Big() {
⋯ +31 lines — whole declaration at big.go:4-35 ⋯

// Small is small.

F10 Medium Confirmed from code

One lazy-description timeout permanently abandons the whole batch

internal/lazydesc/filler.go:157 fill · :236 run (the ctx.Done() arm) · :210 recordAttempts

Trigger

descriptions.lazy on (the default), a provider configured, a cold repository, and a fill that exceeds descriptions.lazy.timeout_seconds (8s by default) — which is precisely the situation on the first reads after installation, when the filler has the most to do and the provider is slowest.

Mechanism

fill calls recordAttempts(pending) for the whole claimed set regardless of outcome, and run's deadline arm returns whatever happened to be buffered while leaving the outstanding batches to finish into a channel nobody reads. So targets whose batch was still in flight are:

  • recorded in the persisted attempt ledger with their current fingerprint, and
  • discarded even if their descriptions arrive a moment later.

The ledger only expires on a fingerprint change, so those nodes stay undescribed until their source is edited. The comment justifying the record — “a resource the model declines to describe would otherwise be re-planned by every read” — is about a refusal, which is durable. A timeout is transient and is being treated as durable.

Effect

The first slow read on a cold repository burns up to max_nodes (40) nodes permanently. Since every intercepted cat and grep is a fresh process, the in-process ledger is not what saves them — the persisted one is what condemns them. The stated behaviour (“Reads are slower on a cold repo and converge on the old speed as it warms up”) becomes “reads stay fast and the repo never warms up”. arac descriptions generate still works, so it is recoverable, but nothing tells the operator to run it.

Fix

Record only what was actually attempted to completion. run already knows which batches returned; have it report the set of targets whose batch completed (successfully or with a provider error) and pass that to recordAttempts instead of the whole pending slice. Targets abandoned at the deadline stay unattempted and get another chance on the next read.

Two smaller companions:

  • Release the in-process claim for abandoned targets too, so a second read in the same long-lived arac serve can retry them.
  • Keep the results that do arrive after the deadline: the worker goroutines already write into a buffered channel, so a write() on a late drain costs nothing and the descriptions were paid for.

The `intercept_id` contract promises “the nearest candidates”; a mistyped ID gets “No such file or directory”

Trigger

Mechanism

`breToRE2` reads a second leading `^` as an anchor rather than a literal

internal/shellcmd/shellcmd.go:1036-1060 breToRE2 (the '^' arm)

Trigger

A POSIX-BRE grep (no -E/-F) whose pattern begins with two carets, or with a caret immediately after \( or \| followed by another caret.

Mechanism

The '^' arm deliberately leaves leading true, because a caret does not give a following * something to repeat. That is correct for * and wrong for a second ^: in BRE only the first caret anchors, and any later one is an ordinary character. ^^foo therefore becomes RE2 ^^foo — two anchors, which matches lines starting with foo — where the real grep matches lines starting with a literal caret.

Effect

A confident wrong answer to a rare pattern: the intercepted search returns matches the real command does not. Exotic, but this function's entire premise is that it must not translate a pattern it cannot vouch for.

Reproduction

breToRE2("^^foo") = "^^foo"       want "^\\^foo"

Asserted by the dormant TestAudit_BREInteriorCaretIsLiteral, currently failing.

Fix

Track “may still anchor” separately from “nothing to repeat”. Add a second flag — anchorable, set true at the start of the pattern and just past \( / \|, and cleared by any emitted character including a caret — and have the '^' arm test that instead of leading. leading keeps its current meaning for the '*' arm, which is right as written.

F18 Low Confirmed from code · not reproduced

The manifest stamps a post-scan mtime, so a write landing mid-scan is invisible afterwards

internal/helper/manifest.go:109-115 SyncManifest · :134 SyncManifestFiles · :422 DiffScanFiles

Trigger

A file written after the parser has read it but before the manifest is stamped. Reachable through parallel sub-agents editing during a guard pre-tool scan, an editor save during arac scan, or a long Python-scanner pass (one subprocess per file).

Mechanism

SyncManifest records fi.ModTime() read at stamping time, not the mtime the parser observed. DiffScanFiles then compares fi.ModTime().After(stamped), which is false for the new mtime — so the file is “unchanged” while the database holds the pre-write parse. Nothing later corrects it: the entry only becomes stale again on a further write.

The else branch is worse in the same direction: when the stat fails it stamps time.Now(), a timestamp that may be ahead of every future write.

Effect

A permanently wrong graph entry for that file, with check-updates reporting clean. Reads of its symbols return stale spans; healStale recovers the ones whose span no longer fits the file, but a same-length edit produces silently wrong source.

Honest caveat: I could not land this in a controlled timing test. On a 25,000-file fixture the window between one file's parse and SyncManifest measured under ~100 ms, and every injected write fell outside it. The mechanism is unambiguous in the code — and the dormant TestAudit_ManifestDoesNotSwallowAWriteDuringTheScan asserts it directly (it does not currently compile, against the newer three-argument signature) — but I am reporting it as a latent race rather than a demonstrated one.

Fix

Stamp the mtime the parser saw, not the one the stamper sees. The scanners already stat each file to decide whether to parse it; carry that time.Time alongside the path in the attempted slice (make it []ScannedFile{Path, ModTime}) and write that value into the manifest. A write during the scan then leaves a strictly newer mtime on disk and the next diff catches it.

Where a pre-parse mtime genuinely is not available, stamp the earliest safe value — the scan's own start time — rather than time.Now(). Erring early costs one redundant re-parse; erring late loses the write.

F21 Low Confirmed from code

A relative operand is resolved against the project root, not the agent's shell — so a same-named file at the root shadows it

internal/cli/guard_untracked.go:76 existingReadFiles · internal/cli/guard_intercept.go:300 namesOnlyUnindexedFiles · :325 namesAnIndexedFile

Trigger

The agent's Bash shell has cd'd into a subdirectory, its command names a relative path, and a file of the same relative name exists at the project root with a different tracked status.

Mechanism

existingReadFiles resolves a relative token as filepath.Join(root, tok). The choice is deliberate and correct in the general case — the hook cannot see the agent's shell cwd, and resolving against its own would answer about a different file. What it does not handle is the collision: from internal/, cat util.go resolves to <root>/util.go, and the tracked-status answer belongs to the wrong file.

Effect

Two asymmetric consequences:

  • Interception (namesOnlyUnindexedFiles): a false “all operands unindexed” refuses a rewrite aracne could have served. Costs one un-enriched read; harmless, because arac cmd re-checks in the agent's real shell.
  • The nudge (namesAnIndexedFile): this one has no second check — whatever it decides is printed to the model. A false positive advertises the aracne read for a file that carries no nodes; a false negative withholds the pointer where it would have been right.

Bounded, and the least-bad resolution given what a hook can see. Listed because the asymmetry is not currently written down where existingReadFiles is used for the nudge.

Fix

Make the ambiguity visible rather than guessing. Have existingReadFiles return, alongside the resolved paths, whether any token was relative and therefore resolved speculatively. Then:

  • namesAnIndexedFile — which requires positive evidence — treats a speculative resolution as no evidence and returns false, so the nudge fires only on a token it could place unambiguously (an absolute path, or a directory inside the root);
  • namesOnlyUnindexedFiles keeps today's behaviour, since a wrong guess there costs nothing.

Claude Code's hook payload does not carry the Bash tool's persistent cwd, so there is no way to resolve it correctly; declining to answer is the honest alternative. If a future payload does carry it, prefer it over the root — the same tier order guardDBPath already uses.
