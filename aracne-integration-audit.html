Ten defects between the model and the graph

An audit of the Claude Code and OpenCode surfaces — the guard hook, the shell classifier, arac cmd, the annotated grep, and the generated integration files. Nine of the twelve were reproduced against a scanned fixture with the built binary; the other three are read off the code and the artifacts it writes, and each entry says which it is.

What was examined

The PreToolUse/PostToolUse guard, command interception and rewriting, internal/shellcmd, arac cmd passthrough fidelity, topogrep output parity against GNU grep 3.11, the MCP server's JSON-RPC handling, arac setup/disable round-trips, and the incremental scan that keeps the graph current under the hooks.

What was excluded

Per the brief: the viz Chat tab, internal/chat, and the internal arac agent REPL. The bug-pipeline agents are only covered where arac setup writes or prunes their files.

What counts as a defect here

Only behaviour the code's own stated contract forbids: a confidently wrong answer, a capability that is manufactured and then withdrawn, or two enforcement paths that disagree. Deliberate divergences are listed separately at the end, unflagged.

F-01 Critical Incremental scan Graph integrity Fixed · tests added

Renaming a source file deletes its declarations from the topology

Resolved. RemoveFileResources now spares any owned symbol whose Location.Path no longer names the file being removed, via a new movedOutOfFile helper. The file node itself is exempt from the test — a file resource carries an empty Location.Path because its identity is its path — and the connection-strip pass reads the same set, so the new file's and the package's ownership edges survive with it.

Verified through the guard on a fresh fixture: 6 resources before the rename, 6 after, arac read Alpha answering from pkg/b.go, the annotated grep keeping its headers, and the only remaining warning the true one — the old file node really is gone. Two unit tests in internal/helper/referrers_test.go and one scan-level equivalence test in tests/incremental_equivalence_test.go; the unit tests fail on the pre-fix code with the exact bogus warning this entry documents. go test ./... green.

One thing the fix does not restore: see F-11. The graph and its edges survive a rename now; a description that aracne generated for a symbol with no doc comment still does not, and that is a separate defect one layer down in the scanners.

Symptom

An incremental scan that sees one file added and another deleted registers the added file first and removes the deleted one second. RemoveFileResources deletes by resource ID, so when the two files declare the same IDs — which is exactly what a rename is in Go, where an ID is module/package.Symbol and carries no filename — the removal takes the declarations the new file has just re-registered.

The graph keeps the new file node and loses every symbol in it. It does not heal: the manifest is stamped with the new file's current mtime, so every subsequent incremental scan sees nothing to do.

Reproduction

Fixture: a two-file Go package, scanned with --all.

$ arac scan --all && arac resource list
Found 6 resources.
  …/pkg/a.go
  …/pkg/keep.go
  example.com/ren/pkg
  example.com/ren/pkg.One
  example.com/ren/pkg.Other
  example.com/ren/pkg.Two

$ mv pkg/a.go pkg/b.go
$ arac scan            # the default incremental scan
[node_removed] example.com/ren/pkg.One was removed from …/pkg/a.go,
    verify …/pkg/b.go which references it via has_function

$ arac resource list
Found 4 resources.
  …/pkg/b.go
  …/pkg/keep.go
  example.com/ren/pkg
  example.com/ren/pkg.Other       ← One and Two are gone

$ arac read One
# UNRESOLVED:
- One: resource "One" not found in topology

And through the harness, which is how a session actually hits it.

$ PostToolUse hook event for mv pkg/a.go pkg/b.go
{"hookSpecificOutput":{"additionalContext":
  "Topology re-synced.\nTopology warnings …
   - [node_removed] example.com/e2e/pkg.Alpha was removed from …/pkg/a.go,
     verify …/pkg/b.go which references it via has_function"}}

$ arac node count
2                                  # was 4

Trigger paths

  • mv / git mv of a .go file inside its package — the classifier calls the command unclassified, so the PostToolUse drift check fires and runs the scan that does the damage.
  • The scan.pre_tool incremental scan in front of the next tool call, if the drift check did not get there first.
  • Renaming or moving the project directory itself. Every path changes at once, so the whole graph is added and then removed: a four-resource fixture came back with one node, and arac scan then printed Warning: detected go under … but indexed 0 files.
  • A branch switch or git checkout that renames a file.

Effect

For the rest of the session the topology answers "not found" for symbols that plainly exist: arac read fails, the annotated grep loses its headers for that file, and read.kinds-gated reads fall through to raw bytes. The model is simultaneously told to verify the file that still contains the declaration, which is a warning it cannot act on.

Recovery requires arac scan --all or touching the renamed file again; a second incremental scan does not recover it. Nothing tells the operator to do either.

Where

  • internal/topology/manager.go:316 — the for _, path := range deleted loop runs after phase 1 and phase 2 have registered the added file
  • internal/helper/manifest.go:491 — RemoveFileResources collects toRemove from the old file node's ownedConnTypes edges and deletes those IDs unconditionally
  • internal/topology/manager.go:114 — IncrementalScan, the enclosing order

Fix applied

Ownership, not rename detection. The removal never asks "was this a rename?" — a question that needs content hashing (defeated by the rename-plus-edit that git mv usually is) or an id-overlap threshold, and that answers per FILE where the graph needs an answer per SYMBOL. It asks "does this resource still say it lives here?", which the graph already knows because phases 1 and 2 have run:

for connType, targets := range fileRes.Connections {
    if !ownedConnTypes[connType] { continue }
    for _, target := range targets {
        if movedOutOfFile(topo, target, fileID) {
            continue
        }
        toRemove[target] = true
    }
}

It is right in every shape: a rename keeps the symbol (its path moved), a real deletion drops it (its path did not), a delete-plus-unrelated-add drops the old and keeps the new, and a symbol re-declared in a third file in the same batch is kept — which is correct, because it exists.

The alternative was reordering the deleted loop above phase 1. It also works, and better than first written up here: ResolveReferrerWarnings, already the last step of IncrementalScan, retires a node_removed whose target is back in the graph, so the transient warnings clean themselves up. Running the two halves as separate scans confirms the resulting graph is fully correct. The ownership guard still won on being four lines inside one function, not moving the phase boundaries reverseCallerFiles and removedSince are written around.

F-02 High Guard · shell scanner Reproduced

A stderr redirect is read as an stdout redirect

Symptom

splitCommandSegments sets redirectsOut on any unquoted > that is not followed by &. It has no notion of a file-descriptor prefix, so 2>/dev/null and 2>>err.log are recorded as "this segment writes its stdout to a file". Only 2>&1 escapes, and by accident — the & check was written for descriptor duplication.

Two consequences

  • Interception silently switches off. interceptableSegment refuses any segment with redirectsOut, so grep -rn foo . 2>/dev/null — one of the most common shapes an agent writes — never reaches the annotated grep, in any mode. Nothing reports this; it simply looks like aracne not helping.
  • A read is classified as a mutation. ShellCommandKeyForArgs takes redirectsOut as its signal that a stream editor writes, so sed -n '1,5p' f 2>/dev/null and awk 'NR<=3' f 2>/dev/null come back as edit. Under blocked_tools: ["edit"] they are denied outright, with a message telling the model to use arac edit on a command that reads. With the default empty blocked_tools they still make mayHaveWrittenSource true, so every such read pays a post-call drift check and manifest walk.

Reproduction

mode: mcp · blocked_tools: ["edit"] · PreToolUse events

$ command: sed -n '1,5p' src/big.go
(no output — allowed, as it should be)

$ command: sed -n '1,5p' src/big.go 2>/dev/null
{"hookSpecificOutput":{"permissionDecision":"deny",
  "permissionDecisionReason":"Blocked by aracne config (blocked_tools: edit).
   aracne: `echo '{\"edits\":[…]}' | arac edit` applies several replacements …"}}

$ command: awk 'NR<=3' src/big.go 2>/dev/null
{"hookSpecificOutput":{"permissionDecision":"deny", …}}

mode: intercept_line_ranges · the rewrite that does not happen

$ command: grep -rn "foo" .
{"hookSpecificOutput":{"updatedInput":{"command":"…/arac cmd -- grep -rn \"foo\" ."}}}

$ command: grep -rn "foo" . 2>/dev/null
(no output — not intercepted, runs as plain grep)

Where

  • internal/cli/guard.go:592–597 — case '>' in splitCommandSegments
  • internal/cli/guard.go:466 — the redirectsOut field comment, which says "an unquoted > or >>" and means stdout
  • internal/cli/guard_intercept.go:98 — the interception refusal
  • internal/toolspec/toolspec.go — ShellCommandKeyForArgs, the streamEditors branch

Fix

At case '>', look back over the immediately preceding raw runes while they are digits. An empty digit run, or exactly 1, is a stdout redirect and sets curRedirect; any other descriptor (2, 3, …) does not. The look-back must read the raw runes slice rather than the accumulated segment text, for the same reason isRedirectAmpersand already does — quote characters have been dropped from cur.

&>file and &>>file genuinely do redirect stdout and must keep setting the flag; isRedirectAmpersand already recognises the pair, so the & arm needs the same treatment as 1>.

Add cases to internal/shellcmd/shellcmd_test.go's companion in internal/cli/guard_intercept_test.go: 2>/dev/null must intercept, >out.txt must not, 2>&1 must intercept, &>log must not.

F-03 High shellcmd · arac cmd Reproduced

A non-recursive grep on a directory is answered as a recursive search

Symptom

parseGrep tracks sawRecursive, but only consults it for the path-less form (grep -r foo with no operand). When an operand is present the flag is dropped on the floor, and grepRoots walks any directory operand recursively.

POSIX grep does not. GNU grep 3.11 prints grep: pkg: Is a directory and exits 2; BSD grep behaves equivalently. Only rg, ag and ack — already handled by searchesCwdByDefault — recurse without being asked.

Reproduction

$ /usr/bin/grep -l Add .
/usr/bin/grep: .: Is a directory
exit 2

$ arac cmd -- grep -l Add .
pkg/util.go
exit 0

$ /usr/bin/grep Add pkg
/usr/bin/grep: pkg: Is a directory
exit 2

$ arac cmd -- grep Add pkg
# pkg/util.go:4-6 — Add adds two ints.
pkg/util.go:func Add(a, b int) int {
exit 0

The same on this repository, through arac cmd:

$ arac cmd -- grep -l TopologyManager internal/cli
internal/cli/bug.go
internal/cli/check_updates.go
internal/cli/cmd.go
…                                # real grep: "Is a directory", exit 2

Effect

This is precisely the failure serveCommand documents for rg on a box without ripgrep, in the other direction: aracne manufactures a capability, the model learns the spelling, and the capability vanishes the moment the command carries a flag shellcmd does not model.

$ arac cmd -- grep Add pkg          # served, exit 0
# pkg/util.go:4-6 — Add adds two ints.
pkg/util.go:func Add(a, b int) int {

$ arac cmd -- grep -o Add pkg       # -o is unmodelled → passthrough
grep: pkg: Is a directory
exit 2

A model that has been rewarded for grep pat somedir will type it again with -o, -h or -P and get an error, having been given no way to tell the two apart.

Where

  • internal/shellcmd/shellcmd.go:629, 685, 848 — sawRecursive is declared, set, and used only in the no-operand branch; it never leaves parseGrep
  • internal/cli/cmd.go:422 — grepRoots hands any operand to topogrep, which walks a directory
  • tests/grep_parity_test.go — every directory case in the suite passes -r, so the shape is untested rather than pinned

Fix

Carry the flag out of the parser: add Recursive bool to shellcmd.GrepRequest and set it from sawRecursive. The parser stays pure — it still does no I/O — and the decision lands where the filesystem is already being consulted.

In grepRoots, when req.Grep.Recursive is false and the tool is not in searchesCwdByDefault, os.Stat each operand and return ok == false if any is a directory. That falls through to passthrough(), which reproduces the real error and exit status byte for byte — the same trade commandIsAvailable already makes.

Note that a directory operand reached through -r must keep working, and that a single file operand is unaffected either way.

F-04 Medium arac setup · OpenCode Reproduced

OpenCode's permission block bypasses BlockableInMode

Symptom

initOpenCode gates on cfg.GuardBlocksNativeReads() and then reads the raw blocked_tools list. The Claude Code guard does not: it filters the same list through cfg.BlockableInMode(), which drops grep outside mcp mode because search is intercepted in every mode and refusing it would deny a command aracne was one step from answering.

So in mode: "cli" with blocked_tools: ["read", "grep"], the two harnesses enforce different policies from the same config — and the generated contract describes the Claude one to both of them.

Reproduction

$ .aracne/config.json: mode "cli", blocked_tools ["read","grep"]
$ arac setup -y

$ cat .opencode/opencode.json | jq .permission
{
  "read": "deny",
  "edit": "allow",
  "bash": { "*": "allow",
            "cat *": "deny", "head *": "deny", "tail *": "deny", "less *": "deny",
            "grep *": "deny", "rg *": "deny" }
}

$ Claude guard, same config, PreToolUse Bash grep -rn Greet pkg/util.go
(no output — not denied)

$ cat CLAUDE.md   # and AGENTS.md — the same document
## Tool Guard
This project denies shell and native read calls that aracne can answer instead
(`read` in its `blocked_tools`).      # grep correctly absent

Effect

An OpenCode session refuses grep … and rg … with no explanation the contract offers, and no alternative: the annotated grep in that mode arrives as the command being refused. The comment directly above the code names this exact failure — "the one the operator notices is this one, because it refuses silently".

Related, same block. A static glob map cannot reproduce the guard's two denial exemptions (operatesOutsideProject and readsOnlyUntrackedFiles), so cat CHANGELOG.md and cat /tmp/repro.py are refused on OpenCode where the Claude guard deliberately lets them through. That is inherent to the mechanism rather than a coding error, but it belongs in the same review: it is the regression guard_untracked.go was written to end.

Where

  • internal/cli/setup.go:130–133 — blocked = toolNameSet(mainEff.BlockedTools)
  • internal/helper/config.go:1354 — BlockableInMode, the filter that is skipped
  • internal/cli/guard.go — loadGuardConfig, which does apply it
  • internal/cli/setup.go:591, 598 — openCodeGrepDenyPatterns, openCodeBashPermission

Fix

One line: blocked = cfg.BlockableInMode(toolNameSet(mainEff.BlockedTools)). The GuardBlocksNativeReads() guard around it becomes redundant — BlockableInMode already returns an empty set when the mode may block nothing — so the branch can collapse to the single call.

Then pin it: a test asserting that for each of the four modes, the set initOpenCode writes and the set loadGuardConfig enforces are equal for the same config. tests/setup_test.go is the right home; it already reads the generated OpenCode config.

F-05 Medium topogrep Reproduced

grep -c drops zero-count files and reorders the rest

Symptom

Result.Counts is built only from matches, so a searched file with no hits never gets a key and formatCounts cannot print its row. GNU grep prints path:0 for every file it was asked about. formatCounts also sorts its paths, where grep emits them in the order the operands were given.

The single-file case is correct — a bare number, and 0 with exit 1 when nothing matched. It is multi-file and recursive -c that diverge.

Reproduction

$ /usr/bin/grep -c Add pkg/util.go main.go
pkg/util.go:2
main.go:0

$ arac cmd -- grep -c Add pkg/util.go main.go
pkg/util.go:2
(main.go absent)

$ /usr/bin/grep -c "func " internal/cli/guard.go internal/cli/cmd.go
internal/cli/guard.go:21
internal/cli/cmd.go:16

$ arac cmd -- grep -c "func " internal/cli/guard.go internal/cli/cmd.go
internal/cli/cmd.go:16       # sorted, not operand order
internal/cli/guard.go:21

Effect

The parity brief in tests/grep_parity_test.go classifies -c as EXACT — "a question whose answer is a NUMBER … where adding changes the answer rather than enriching it". Removing a row changes it just as surely. A caller doing grep -rc pat . | awk -F: '$2==0', or reading counts positionally, gets a different answer from the one it wrote the pipeline against.

Why the suite is green. TestCountModeCountsWhatTheRealGrepCounts builds its expectation with if ok && n != "0", which discards exactly the rows that go missing, and then only checks the rows aracne did emit. The test cannot fail on this.

Where

  • internal/topogrep/grep.go:371 — out.Counts[m.Path]++, the only writer
  • internal/topogrep/grep.go:714 — formatCounts, which sorts and can only render what Counts holds
  • tests/grep_parity_test.go:411 — the expectation filter that excuses it

Fix

In count mode, seed Counts with 0 for every file walkSearch visited, before the match loop increments it. The walker already calls visit(path) per file, so the hook exists.

For ordering, carry the operand order through: when every root is a file, formatCounts should emit in Options.Roots order and fall back to sorted paths for a directory walk (grep's own directory order is not reproducible, and sorted is the honest substitute). Then drop the n != "0" filter from the parity test so the property is actually pinned.

F-06 Medium Guard · warnings Reproduced

Topology warnings reach the model in a random order

Symptom

currentWarningIDs ranges over the warnings map to build its slice, and neither unreportedWarnings nor formatDriftWarnings sorts it. Go randomises map iteration, so the PostToolUse block a model reads after an edit is shuffled on every run. arac warnings list, answering the same question, sorts by kind then source.

Reproduction

One edit widening four signatures with six callers each — 24 warnings, three identical runs.

run 1  - [signature_changed] function A … verify caller …ord.U6
       - [signature_changed] function C … verify caller …ord.U5
       - [signature_changed] function B … verify caller …ord.U3

run 2  - [signature_changed] function C … verify caller …ord.U3
       - [signature_changed] function B … verify caller …ord.U4
       - [signature_changed] function C … verify caller …ord.U2

run 3  - [signature_changed] function D … verify caller …ord.U1
       - [signature_changed] function D … verify caller …ord.U4
       - [signature_changed] function A … verify caller …ord.U5

Effect

The contract's one non-negotiable instruction is "act on any topology warning that comes back". A shuffled list of two dozen warnings interleaving four callees and six callers is materially harder to work through than a grouped one, and the model has to re-derive the grouping itself from text that is re-sent on every request.

It also makes the hook's own output untestable and un-diffable: two runs over identical state produce different bytes, so a golden-output test for the warning channel cannot be written.

Where

  • internal/cli/guard_warnstate.go:145 — unreportedWarnings
  • internal/cli/guard_warnstate.go — currentWarningIDs, the map range
  • internal/cli/guard_drift.go:184 — formatDriftWarnings, the renderer
  • internal/cli/warnings.go — RunWarningsList, which does sort; the two should agree

Fix

Sort in formatDriftWarnings — it is the one renderer both hooks go through (runClaudeUpdateFileHook calls it too). Use the comparator RunWarningsList already has: kind, then SourceID, then TargetID as a tiebreak, since a signature change fans out to several callers of one callee and grouping them is the whole readability win.

Lift that comparator into a shared helper so the CLI and the hook cannot drift; sorting in unreportedWarnings instead would leave writeReportedWarnings's own sort as the only guarantee and miss the update-file hook's path.

F-07 Medium arac setup · permissions Artifacts verified · effect inferred

Nothing pre-approves the command the guard rewrites into

Symptom

Interception replaces the model's command with /abs/path/to/arac cmd -- <original> through updatedInput. arac setup writes a permissions.allow block that names every mcp__aracne__* tool — precisely so the harness does not prompt on each call — and no rule at all for the rewritten Bash command.

The generated settings.json on a project in cli mode with blocked_tools set:

"permissions": {
  "allow": [
    "mcp__aracne__node_list_no_description",
    "mcp__aracne__read",
    "mcp__aracne__read_resource",
    "mcp__aracne__update_description",
    "mcp__aracne__warnings_list"
  ]
}                       # no Bash rule of any kind

Effect

Any Bash allow-rule a user or team has written — Bash(grep:*), Bash(head:*), Bash(sed:*) — is written against the command the model types, not against the command that ends up running. Once the guard rewrites, those rules no longer match their target, and the very commands aracne is best at are the ones that stop being pre-approved.

Confidence. The absence of the rule, and the shape of the rewrite, are verified in the generated files. Whether the harness re-evaluates permissions against updatedInput or against the original was not reproduced here — it needs a live session with a Bash allow-rule in place. Treat this as a one-session check before release rather than a confirmed defect.

Where

  • internal/cli/guard_intercept.go:45 — interceptCommand, which builds the replacement from os.Executable()
  • internal/cli/native_hooks.go:249 — claudeMCPPermissionRules, the only allow-rules setup writes
  • internal/cli/native_hooks.go — writeClaudePermissions

Fix

Two options, and they are not exclusive:

  • Have writeClaudePermissions add a rule covering the rewritten form — Bash(<aracBinary()> cmd:*) — beside the MCP rules, upserted by the same prefix-strip so it self-heals across re-runs. The binary path is already resolved there by aracBinary(), which the hook commands use.
  • Or have emitPreToolRewrite return permissionDecision: "allow" alongside updatedInput. That is a stronger statement — aracne is answering the call, not asking to — and it makes the rewrite invisible to the permission layer entirely. It also means the guard must be certain, which after F-02 and F-03 it is closer to being.
F-08 Low CLI · db resolution Code-verified

arac scan is the one verb that can create a second project

Symptom

ProjectDBPath exists because a verb run from a subdirectory used to build a second, partial topology there — its doc comment says so at length. Every verb routes through it. RunScan does not: it takes -output with the literal default .aracne/topology.db and passes it straight to manager.Load.

So cd internal/cli && arac scan inside a configured project writes internal/cli/.aracne/topology.db and a fresh default config beside it. Every later verb run from that subdirectory then prefers the nested database, because ProjectDBPath stops at the first hit walking up.

Effect

A partial graph answering reads under default (cli) semantics regardless of the real project's mode, plus a stray .aracne/ directory. This is the exact situation arac init refuses by name — "This directory is inside a project aracne already configures at …" — so the two commands disagree about whether it is allowed.

Low severity because the contract tells the model never to ask for a re-scan, and a person scanning a subdirectory on purpose is a real use case. It is listed because the inconsistency is the kind that surfaces once and then wastes an afternoon.

Where

  • internal/cli/scan.go:22 — output := fs.String("output", ".aracne/topology.db", …)
  • internal/cli/guard_paths.go — ProjectDBPath and the bug it documents
  • internal/cli/init.go — the outer-project refusal arac scan lacks

Fix

Route the default through ProjectDBPath like every other verb — it already leaves an explicitly-passed -output alone, which is the escape hatch a deliberate nested scan needs. Pair it with ProjectRootFor for the scan root so a scan started from a subdirectory indexes the project, matching InitRegistry.

If a bare arac scan in a subdirectory should stay a way to create a nested project, say so where arac init says the opposite: print the outer project's root and require an explicit -root . or -output.

F-09 Low topogrep · output Reproduced

A recursive search drops the ./ prefix real grep prints

Symptom

grep -rn pat . prints rows rooted at the operand — ./src/big.go:3:…. aracne's rows are relative to the topology root and carry no ./.

$ /usr/bin/grep -rn --include=*.go F1 .
./src/big.go:3:// F1 does thing 1.
./src/big.go:4:func F1(a int) int {

$ arac cmd -- grep -rn --include=*.go F1 .
src/big.go:4:func F1(a int) int {
src/big.go:3:// F1 does thing 1.

Effect

Cosmetic for a human and for most pipelines, since both spellings resolve. It matters for the one shape the interception rules explicitly permit — piping a search into a line filter — where a pattern anchored on ^\./ silently matches nothing, and for | sort -u-style de-duplication across a mixed set of intercepted and unintercepted searches.

The codebase treats this class as a real defect elsewhere: GrepRequest's comment on -H/-n is that "either one moves the field a caller reads". Here the field's contents change rather than its position.

Where

  • internal/cli/cmd.go:483 — displayRoot, which relativises against the cwd
  • internal/topogrep/grep.go — the row renderer, which echoes the walked path

Fix

Echo the operand as the caller spelled it. When a search root is given as . or as a relative path, join the walked path onto that literal prefix rather than re-deriving it — grep's rule is simply "the operand, then the rest of the path". displayRoot already has the operand in hand at the point where it discards it.

F-10 Low arac setup · hooks Code-verified

The edit-sync hook and the guard disagree about what a native edit is

Symptom

The guard's matcher is derived from toolspec.nativeToolToKey and comes out as Bash|Edit|Grep|MultiEdit|NotebookEdit|Read|Write. The edit-sync hook next to it is hand-written as "Edit|Write|MultiEdit" — the exact drift NativeToolNames() was introduced to end, one file away from the comment that explains it.

claudeHookPaths has the matching gap: it reads file_path, filePath, path and nested edits, but not notebook_path, so even if the matcher were widened the hook would find no path to re-index.

Effect

Small, because the plugin is opt-in and no shipped path enables it, and because the guard's own drift check covers NotebookEdit either way (driftCheckApplies maps it to edit). A project that turns the plugin on for the inline sync gets that sync for Edit/Write/MultiEdit and the slower drift path for notebooks, with nothing saying so.

Where

  • internal/cli/native_hooks.go:44 — "matcher": "Edit|Write|MultiEdit"
  • internal/cli/native_hooks.go — guardHookMatcher, derived and correct
  • internal/cli/update_file.go — claudeHookPaths, no notebook_path
  • internal/toolspec/toolspec.go — nativeToolToKey, the source of truth

Fix

Derive the edit-sync matcher the same way the guard's is: filter toolspec.NativeToolNames() to the names whose key is edit or write and join them. Add notebook_path to claudeHookPaths's key list, and extend TestGuardHookMatcherCoversNativeTools to cover both matchers so a name added to the map can only be forgotten in one place, not two.

F-11 Medium Scanners · descriptions Fixed where the ID survives

Moving a file discards the descriptions of every symbol in it

Resolved for the id-stable half. TopologyManager.restoreDescriptions refills a blank description from the pre-update snapshot by id, in IncrementalScan after the deletion pass and inside UpdateFile's finish so both entrances agree. It is the rule FullReScan already applies to a cold rescan and the rule each scanner applies within a file — stated once more where ids, not files, are the unit of identity.

Which languages that reaches is decided by their id schemes, not by the fix. Measured before and after, per language, on the matrix in the next row: Go and Java are fixed — a Go id is module/package.Symbol and a Java id is an FQN from the package declaration plus a signature, so neither moves with the file. Python, JavaScript, TypeScript and Rust are not reachable this way: they are modules-first and mint a new id from the new filename, so there is no surviving id to carry anything to. That is the identity-remap work, deferred.

Java gets a bonus from the same property: moving A.java to a different directory while the package declaration stays — the src/ → src/main/java/ restructuring — now keeps its descriptions too. Verified.

Tests: tests/description_rename_test.go — a six-language table asserting the invariant a description follows a surviving id, plus per-language ordinary-edit preservation and the update-file two-call rename the hooks drive. It also pins each language's idSurvivesRename, so a change to an id scheme fails loudly here instead of silently widening or narrowing what the carry-over covers. Without the fix, the go, java and update-file cases fail; the ordinary-edit cases pass either way, which is what shows the scanners' own preservation is intact. go test ./... green, both build flavours.

Symptom

Each scanner carries a description across a re-parse only when the resource was owned by the same file before: goscanner builds oldFunctions from oldFile.Functions() and fills a blank description from it. On a rename the file being registered is brand new, so that map is empty — and the descriptions sitting on the identical ids under the old path are never consulted.

It bites the descriptions that cost something. A Go function with a doc comment gets its description re-harvested from source on every parse, so it is never at risk. A function with no doc comment — precisely the one an arac descriptions generate sweep paid a model to describe — comes back blank.

Reproduction

Four undocumented functions, described, then the file renamed in place.

$ arac scan --all
$ arac update-description example.com/x/pkg.One function "Description for One."   (×4)
   example.com/x/pkg.One    desc='Description for One.'
   example.com/x/pkg.Two    desc='Description for Two.'
   …

$ mv pkg/a.go pkg/b.go && arac scan
   example.com/x/pkg.One    desc=''          # id unchanged, prose gone
   example.com/x/pkg.Two    desc=''

$ and an ORDINARY edit of the same file, for contrast
$ echo '…func Three…' >> pkg/a.go && arac scan
   example.com/x/pkg.One    desc='Description for One.'   # preserved
   example.com/x/pkg.Three  desc=''

Moving to another folder loses them twice over — the Go id changes too.

$ mv pkg/a.go internal/other/a.go && arac scan
   example.com/x/internal/other.One   desc=''
   example.com/x/internal/other.Two   desc=''

Per language

Same fixture in each: one undocumented declaration, a description hung on it, then the file renamed inside its own folder and an incremental scan. What decides the outcome is whether the language's id moves with the file.

language     id after `mv a → b`              description  before → after fix
go           example.com/g/pkg.Alpha          ''  →  'DESC'     id is module/package.Symbol
java         com.example.A.alpha()            ''  →  'DESC'     id is FQN + signature
python       mod_a.alpha → mod_b.alpha         ''  →  ''          modules-first: new id
javascript   a.alpha → b.alpha                 ''  →  ''          modules-first: new id
typescript   a.alpha → b.alpha                 ''  →  ''          modules-first: new id
rust         r::a::alpha → r::b::alpha         ''  →  ''          module IS the filename

an ordinary edit of the same file, all six languages, both before and after:
             'DESC' preserved                 ← each scanner's own file-keyed carry-over

So the fix is language-agnostic in its implementation and language-dependent in its reach, and the reach is exactly the set of languages whose id survives. The other four keep their descriptions through an ordinary edit as they always did; what they still lose is a rename, and that needs the id to be remapped, not the description to be carried.

What does and does not recover it

  • Rename in place, arac scan --all run first: recovered. FullReScan matches by exact id, and a same-package rename does not change ids.
  • Rename in place, an incremental scan run first: lost for good. The description is already out of the database, and --all matches against the database. The guard runs an incremental scan before every tool call, so in a session this is the case that happens.
  • Folder move, --all run first: still lost. MatchDescriptions has a moved_src tier keyed on kind + name + parent + source hash that is designed for exactly this, but BuildDescriptionRecords computes that hash by reading the file at the path the old topology recorded — which the move has just emptied. The tier can never fire on a re-scan after a move.
  • The sidecar does work, because it is written while the files are still in place: arac descriptions export -out d.jsonl → move → scan → arac descriptions import -in d.jsonl restored 2 of 2 at the name_source tier. The export even says so: "2 have a source hash (needed to survive a file move)".

Where

  • internal/topology/scanner/goscanner/scanner.go:405–470 — the carry-over, keyed on oldFile; jsscanner and rustscanner have the same shape
  • internal/topology/manager.go:541 — the id-keyed rule FullReScan applies, which the incremental path has no equivalent of
  • internal/helper/descriptions_sidecar.go:418 — hashSpan, which reads the old path off disk and returns "" once it is gone

Fix

Applied: one language-agnostic pass, in the place that already has the data. IncrementalScan deep-clones the pre-update graph into beforeResources for the reverse-caller sweep. After the deletion pass, fill any blank description from it by id — the same rule FullReScan applies at manager.go:541, and the same rule each scanner applies per file, stated once more where ids rather than files are the unit of identity. UpdateFile gets it inside finish, so the hook path and the scan path cannot answer differently:

for id, res := range topo.Resources {
    if res.Description != "" { continue }
    if old, ok := beforeResources[id]; ok && old.Description != "" {
        res.Description = old.Description
        topo.Resources[id] = res
    }
}

It cannot resurrect a cleared description (descriptions clear writes the database directly, so the next scan's beforeResources is already empty), and it defers to a freshly harvested doc comment, which arrives non-empty.

Still open, deferred by decision: the four modules-first languages, and any move that changes the id. Those need resource_alias and the identity remap (helper.MatchDescriptions), today reachable only from FullReScan — and its moved_src tier needs the source hash to be taken while the old path still exists, which a re-scan after the move cannot do. The cheap interim is to make the loss discoverable: when a scan drops descriptions it cannot re-home, say so, and point at arac descriptions export/import, which does work.

F-12 Low Incremental scan Reproduced

A package whose last file moves away is left behind as a phantom

Symptom

Move a package's only file to another directory and the incremental scan builds the new package correctly but never retires the old one. The package node survives with no files, and every caller keeps its uses_package and __call_sites edges pointing at it.

Found by feeding the move to assertIncrEqualsFull, the harness that compares an incremental result against a cold full scan of the same tree:

resource "eqmove.main" differs:
  full: function|main|go||…/main.go|{…}|
  incr: function|main|go||…/main.go|{…}|__call_sites=eqmove/pkg.Add=>>{…};uses_package=eqmove/pkg;
resource "eqmove/pkg" present after incremental but absent from full rescan (stale row)

Confirmed pre-existing: the failure is byte-identical with and without the F-01 fix, which cannot reach it — movedOutOfFile only spares resources whose recorded path moved, and a package node carries no path and is never owned by a file.

Effect

A phantom package in the graph: it can be listed, it appears in a caller's context block, and a read of it returns a package with nothing in it. The stale __call_sites entry is the one with teeth — that edge is what signature_changed is decided against, so a warning could be raised or discharged against a call site that no longer exists.

Low because it needs a cross-directory move of a package's last file, and because arac scan --all clears it.

Where

  • internal/topology/manager.go:316 — the deletion path handles files and the symbols they own; nothing prunes a container left empty by it
  • internal/helper/manifest.go — ownedConnTypes covers has_function and friends, not has_file
  • tests/incremental_equivalence_test.go — assertIncrEqualsFull reproduces it in about fifteen lines

Fix

After the deletion loop, drop any package/module node whose has_file set is now empty, and run it through the same referrer strip so the callers' uses_package and __call_sites edges go with it. Then add the move as a case in assertIncrEqualsFull — it is the harness that found it, and it will keep it fixed.

Behaviour confirmed as deliberate, not filed

Each of these diverges from the plain command and each is argued for in the code or pinned by a test. They are listed so the register can be read as complete: they were examined and deliberately not reported.

  • ·Tiered result ordering. Title hits, then description hits, then line hits — where grep is in file order. Pinned by the parity suite as a permitted divergence.
  • ·Description-tier rows. grep -n Retries f returns a declaration line that does not contain the pattern, under a header that explains why, and exits 0 where grep exits 1. This is the product.
  • ·Annotation lines counting toward a downstream head -N. Measured and accepted in consumer.go; the alternative was refusing 41 of 133 piped greps.
  • ·The 200-row default cap and its trailer. Documented at the top of topogrep as the first of two rules.
  • ·Pruned directories — .git, .aracne, vendor, node_modules, the cache trees. A deliberate list, and deliberately not a dot-prefix rule.
  • ·A window widening to its declaration. sed -n '10,14p' answering from line 9 with an elision marker is the framing the contract promises.
  • ·read.kinds refusing an intercepted cat rather than passing it through — argued in resolveReadOperand.
  • ·Warn-only blocked_tools by default, and the hard pre-tool scan being rejected by Validate and re-mapped by EffectivePreToolScan.

Checked and found sound

Exercised against the built binary on a scanned fixture and on this repository. Recorded because the value of a defect register is partly in what it clears.

  • ✓Interception guard rails. Pipes into an opaque consumer, $(…) and backtick substitution, subshells, stdout redirects, heredocs, sudo and unknown wrappers, for … do cat $f; done, and a second arac pass — all correctly left alone.
  • ✓Segment-wise splicing. ls && head -3 f && echo done and a; b rewrite the read segments in place and leave every other byte, including quoting.
  • ✓Passthrough fidelity. cat, head, tail, sed -n, awk NR on untracked and mixed operands come back byte-identical, including ==> f <== banners and a missing trailing newline.
  • ✓Grep flag handling. -i -w -x -F -E, BRE→RE2 translation, -A/-B/-C with grep's own -- separators, per-file -m, repeated --include/--exclude/--exclude-dir, and the -H/-n field rules.
  • ✓MCP protocol. String and numeric ids echoed verbatim, ping, notifications suppressed, omitted arguments normalised, missing tool name as -32602, and a clean initialize/tools/list/tools/call round trip.
  • ✓Setup and disable. Idempotent across re-runs; a user's own PostToolUse hook and permissions.allow entries survive setup and are restored intact by disable; the injected CLAUDE.md block is replaced, not stacked, and removed cleanly.
  • ✓Native-edit reporting. A signature change made outside aracne produces the right signature_changed warning through the PostToolUse drift path, and the ledger suppresses the duplicate.
  • ✓Generated plugins. Both OpenCode plugins parse under Node 24; the Warning number 0 probe matches what arac update-file prints.
  • ✓Guard latency. ~0.10 s per PreToolUse call on this repository with the default incremental pre-tool scan.
  • ✓Build and tests. go build ./... and go test ./... clean before and after every experiment.
