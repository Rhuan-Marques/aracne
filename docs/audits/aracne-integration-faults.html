The guard and the interception path

Ten faults. The first four all produce a silently different answer to a command the model typed, which is the one failure class internal/shellcmd's package doc says the design exists to refuse.

GUARD-01

A command substitution between a producer and its consumer defeats the pipeline-safety check

HighReproduced

internal/cli/guard_intercept.go:186 pipesIntoLinePreservingConsumers · internal/cli/guard.go:524 splitCommandSegments

Requirements

Any mode (grep is intercepted in all four). A single Bash command in which the grep segment contains $(…), a backtick substitution, or ${VAR}, and which pipes into an opaque consumer.

What happens

pipesIntoLinePreservingConsumers asks whether segments[i+1].pipedInto is true. But the scanner cuts a new segment at every (, ), backtick and {, so the substitution's body lands between the producer and the stage that actually reads its stdout. The neighbour is the substitution, not the consumer; pipedInto is false on it, the walk concludes "feeds no pipe", and the rewrite goes ahead.

This is exactly the adjacency break the 2>&1 fix was written for (isRedirectAmpersand), on a path that has no equivalent rule. The depth field already records the nesting the check would need.

Effect

The consumer is handed aracne's annotated rendering instead of grep's match lines. A count, a cut, a sort or an xargs then operates on different text, and nothing in the output marks the substitution.

Fix

Find the consumer at the producer's own depth rather than at i+1: walk forward skipping segments whose depth is greater than segments[i].depth, and evaluate the first same-depth segment. Cheapest safe alternative: refuse interception outright when any segment between i and the next same-depth segment sits deeper.

Reproduction 
$ bash -c 'grep -rn Helper $(echo .) | wc -l'
2
$ bash -c 'arac cmd -- grep -rn Helper $(echo .) | wc -l'
4

# the guard does rewrite it — all three of these come back with updatedInput:
grep -rn Helper $(echo .) | wc -l
grep -rn Helper `echo .`   | wc -l
grep -rn Helper ${PWD}     | wc -l

# while the un-nested forms are correctly refused:
grep -rn Helper . | wc -l          → no rewrite
( grep -rn Helper . ) | wc -l      → no rewrite
GUARD-02

Pipe consumers are classified by command word, so grep -c and head -c are treated as line-preserving

HighReproduced

internal/shellcmd/consumer.go:80 ClassifyConsumer · internal/cli/guard_intercept.go:209 stdinReader

Requirements

Any mode. A shell grep piped into grep or head/tail carrying a flag that changes what the stage does with its lines.

What happens

ClassifyConsumer takes a single word and looks it up in a five-entry map. The module's own doc comment reasons carefully about wc -l — "aracne interleaves # path:a-b annotation lines with the matches, so the count is of a different thing" — and then never inspects a flag. grep -c is that same count spelled with a word the map calls a line filter. head -c N counts bytes, not lines, and lands mid-annotation.

The same blindness covers grep -l, -L, -o, -q and -m downstream.

Effect

A bare number, or a truncated byte prefix, that is confidently wrong and carries nothing to reveal the substitution. Measured on a two-match fixture: | grep -c util returns 2 for real grep and 3 through aracne.

Fix

Give ClassifyConsumer the stage's argv, not its word, and return ConsumerOpaque whenever a flag changes the unit of output: for the grep family -c/--count, -l/-L, -o, -q, -m; for head/tail the -c/--bytes forms (and tail -f). stdinReader already isolates the right segment text — hand it through commandFields instead of taking Fields(...)[0].

Reproduction 
$ /usr/bin/grep -rn Helper . | /usr/bin/grep -c util
2
$ arac cmd -- grep -rn Helper . | /usr/bin/grep -c util
3

$ /usr/bin/grep -rn Helper . | head -c 40
./pkg/sub/util.go:3:// Helper does a thi
$ arac cmd -- grep -rn Helper . | head -c 40
# example.com/proj/pkg/sub.Helper — He
GUARD-03

The 200-match content cap is applied before the downstream filter, dropping a third of the matches

HighReproduced

internal/topogrep/grep.go:56 DefaultHeadLimit · internal/topogrep/grep.go:509 effectiveLimit · internal/cli/cmd.go:359 serveGrep (never sets HeadLimit)

Requirements

Any mode. A shell grep matching more than 200 lines, piped into a line filter the guard permits — which the design notes say is 97% of real piped greps (| grep -v … | head -N).

What happens

serveGrep leaves Options.HeadLimit at zero, so effectiveLimit returns DefaultHeadLimit = 200 for content mode. The intercepted grep therefore emits at most 200 matches plus a trailer saying how many were withheld. pipesIntoLinePreservingConsumers lets the pipeline through on the reasoning that "aracne returns a list of matches too, so both still mean the matches, minus the test ones, first 30" — but aracne's list is a capped list, and the trailer that says so is a plain line the downstream filter treats like any other, or that head -30 discards outright.

There is also no way out from the shell: no grep flag maps onto head_limit, and the trailer's own advice (--include, a path, -m N) cannot recover the missing matches.

Effect

Measured on this repository: grep -rn dbPath internal/cli | grep -v _test yields 181 lines from real grep and 120 through aracne — two of which are advisory, so ~118 real matches, a 35% loss with no marker left in the stream. The model reads it as the complete answer.

Fix

When the segment feeds a pipe, run the search uncapped and unannotated — set HeadLimit: -1 and force plain rendering, since the consumer is a program and the headers were for a reader anyway. If that is unacceptable on cost grounds, the honest alternative is to refuse interception for a piped grep whose result would truncate, which is knowable after the search and before the answer is printed.

Reproduction 
$ arac cmd -- grep -rn dbPath internal/cli | tail -1
… 81 more match(es) not shown (showing 200 of 281). Narrow with …

$ /usr/bin/grep -rn dbPath internal/cli | /usr/bin/grep -cv _test
181
$ arac cmd -- grep -rn dbPath internal/cli | /usr/bin/grep -cv _test
120        ← 61 matches gone, silently
GUARD-04

Intercepted grep re-orders matches, so | head -N selects a different set

MedReproduced

internal/topogrep/grep.go:342 tier sort in SearchWith · internal/shellcmd/consumer.go:54 "head": ConsumerCapper

Requirements

Any mode. A shell grep piped into head or tail.

What happens

Results are sorted by tier first (title match, then description match, then content match) and only then by path and line. Real grep emits in walk order. ConsumerCapper is documented as safe because head and tail "preserve order" — true of the consumer, but the producer already changed it.

Effect

grep -rn Helper . | head -1 returns ./pkg/sub/util.go:3:// Helper does a thing. from real grep and the annotation line # example.com/proj/pkg/sub.Helper — Helper does a thing. from aracne. On a large search it also decides which 200 survive GUARD-03's cap.

Fix

Two options, and the first is cheap: when the segment feeds a pipe, render in path/line order and drop annotation — the same switch GUARD-03 needs. Otherwise, downgrade head/tail to ConsumerOpaque, which costs the idiom the design measured as most common and is therefore the worse trade.

GUARD-05

The denial proxy resolves a relative operand against the hook's cwd and can serve a different file

HighReproduced

internal/cli/guard_proxy.go:45 proxyRead (os.Stat(target.path)) · internal/cli/guard_proxy.go:159 soleReadTarget · contrast internal/cli/guard_untracked.go:78 existingReadFiles

Requirements

mode: mcp or cli, blocked_tools containing read (opt-in, empty by default), the agent's Bash shell cd'd into a subdirectory, and a same-named file existing at the project root.

What happens

The whole point of guardDBPath is that a hook's working directory is not the agent's — the Bash tool's cwd persists across calls and the hook runs in the session directory. Every other guard path honours that: existingReadFiles only accepts an absolute token or one joined onto the project root. proxyRead does not. It stats the raw operand and then passes it straight to ReadIDs, whose readPathCandidates tries the process cwd first.

Effect

The refusal comes back carrying "Reading it for you, with the context it connects to" and the contents of an entirely different file. Nothing in the message names the path it actually read, so the model has no way to notice. When no same-named file exists at the root the proxy merely returns nothing and the model gets a bare pointer — a lost opportunity rather than a wrong answer, but from the same cause.

Fix

Resolve through the same helper the rest of the guard uses. soleReadTarget should take the project root and return the path existingReadFiles produced, or nothing; and proxyRead should hand ReadIDs that absolute path. A relative operand that resolves nowhere under the root must yield no proxy at all.

Reproduction 
# project root holds util.go; pkg/sub/util.go is the file the agent means
# hook event cwd = project root, agent shell cwd = pkg/sub, command = "cat util.go"

{"permissionDecision":"deny","permissionDecisionReason":
 "Blocked by aracne config (blocked_tools: read). Reading it for you, …

  ```util.go
  package main

  // RootUtil is at the repository ROOT, not in pkg/sub.
  func RootUtil() string {
      return \"I am the ROOT util.go\"
  }
  ```"}
GUARD-06

Native Grep with a directory path never earns the search nudge

MedReproduced

internal/cli/guard.go:206 worthNudging · internal/cli/guard_intercept.go:260 namesAnIndexedFile · internal/cli/guard_untracked.go:94 info.Mode().IsRegular()

Requirements

Any mode. The native Grep tool called with a path argument that names a directory — path: ".", path: "src" — which is how the tool is normally used.

What happens

worthNudging reasons that a Grep "names a pattern and maybe a path glob; with nothing to resolve there is no counter-evidence", and returns true for an empty path list. But a directory is something to resolve: claudeHookPaths extracts it, existingReadFiles drops it because it is not a regular file, and namesAnIndexedFile then reports "no indexed file" — which the caller reads as counter-evidence.

The behaviour is therefore inverted: Grep with no path is nudged, and Grep scoped to a directory full of indexed code is not.

Effect

Interception never sees a native Grep, so the PostToolUse nudge is the only channel by which the model learns the annotated grep exists. For the common call shape that channel is dead.

Fix

Treat a directory operand as evidence in its own right: in namesAnIndexedFile, if a token resolves to a directory under the project root, return true (or ask the topology whether it holds any node under that prefix). Keeping the regular-file test for Read is right; a search scope is a different question.

Reproduction 
PostToolUse, tool_name = Grep

{"pattern":"Helper"}                             → nudge
{"pattern":"Helper","path":"pkg/sub/util.go"}    → nudge
{"pattern":"Helper","path":"pkg/sub"}            → silent
{"pattern":"Helper","path":"."}                  → silent
GUARD-07

In mcp mode the Bash-read nudge fires with no evidence test at all

MedReproduced

internal/cli/guard.go:126-148 — the PostToolUse switch

Requirements

mode: mcp. Any Bash command the classifier reads as a read.

What happens

The event.ToolName != "Bash" arm calls worthNudging before emitting anything, and its comment explains why the evidence test is required: "the nudge has no second check downstream — what it decides is what the model reads". The ModeMCP arm below it emits unconditionally. Neither worthNudging nor operatesOutsideProject is consulted.

Effect

Every cat in an mcp-mode session gets "use mcp__aracne__read_resource" injected into the transcript, including for files with no nodes, files that do not exist, and files outside the project. That is per-call context spent teaching a rule that fails the next time the model follows it — the precise cost worthNudging was written to stop.

Fix

Hoist the two scope tests above the switch so both arms share them: skip the nudge when operatesOutsideProject holds, and, for a Bash read, when namesAnIndexedFile(commandPaths(cmd), dbPath) is false. A Bash command with no resolvable path keeps today's behaviour.

Reproduction 
PostToolUse, tool_name = Bash, mode = mcp

cat main.go              → nudge  (correct)
cat CHANGELOG.md         → nudge  (no nodes)
cat /etc/hostname        → nudge  (outside the project)
cat nonexistent-file.txt → nudge  (does not exist)
ls -la                   → silent

the native path gets this right:
Read{file_path: "CHANGELOG.md"}   → silent
GUARD-08

blocked_tools: ["bash"] does not block Bash, and its refusal advice cannot be followed

MedReproduced

internal/cli/guard.go:87-114 (interception before denial) · internal/cli/guard.go:282 operatesOutsideProject exemption · internal/cli/guard.go:326-329 the fallback reason

Requirements

mode: mcp or cli, with bash in blocked_tools. The docs describe this as "blocking bash blocks the Bash tool entirely".

What happens

Three separate holes, all confirmed:

  • Interception runs before decideGuard, so any shell grep is rewritten and allowed to run — the block is bypassed for the one command class aracne rewrites in every mode.
  • operatesOutsideProject returns an empty decision before the block is evaluated, so rm -rf /tmp/x is permitted while ls -la is denied.
  • The fallback reason is "Use the shell forms aracne answers, or an arac subcommand, instead of this command." Every arac subcommand needs the Bash tool that was just denied — and arac read main.go is itself denied with that same sentence.
Effect

An operator who writes blocked_tools: ["bash"] gets a policy that is neither enforced nor escapable: the commands it does block come back with advice that is guaranteed to fail, so the model loops.

Fix

Make bash the one key that short-circuits: check it at the top of the PreToolUse branch, before interception and before the outside-the-project exemption, and deny with a reason that does not name a shell command. If a total Bash block is not a shape the product wants to support, reject it in Config.Validate rather than half-honouring it.

Reproduction 
mode: cli, blocked_tools: ["bash"]

'ls -la'             → DENY  "…Use the shell forms aracne answers, or an `arac` subcommand…"
'grep -rn Helper .'  → REWRITE to `arac cmd -- grep -rn Helper .` and runs
'rm -rf /tmp/x'      → allowed, no output
'arac read main.go'  → DENY  (advice tells it to run an arac subcommand)
GUARD-09

The guard's internal timeouts sum past the hook timeout arac setup writes

MedFrom source

internal/cli/native_hooks.go:98 "timeout": 30 · internal/cli/guard_drift.go:17 guardScanTimeout = 20s · internal/cli/guard_drift.go:112 driftCheck

Requirements

A repository large enough for a manifest walk plus an incremental scan to approach their bounds.

What happens

driftCheck runs two independently-bounded goroutines back to back: indexHasDrifted (20 s) and then runGuardScan (20 s). Worst case is 40 s against a hook whose declared timeout is 30. The PreToolUse side is tighter but also over: a 20 s pre-tool scan, a 3 s trackedFiles, a 3 s untracked check and a 5 s proxy read reach ~31 s.

Effect

The harness kills the hook. The PostToolUse warning report is lost — and because unreportedWarnings writes the seen-set only after it has produced the report, the loss is recoverable, but the model is told nothing at the moment its edit broke a caller. The warnings arrive attached to some later call instead.

Fix

Derive the hook's timeout from the guard's own budget rather than hard-coding 30, or give driftCheck one deadline shared by both stages. A single context.Context with a guardHookBudget threaded through indexHasDrifted and runGuardScan also makes the arithmetic checkable by a test.

GUARD-10

Warning telemetry labels every batch Bash, including native edits

LowFrom source

internal/cli/guard_drift.go:148 logGuardWarnings("Bash", fresh)

Requirements

ARACNE_GUARD_LOG set — i.e. a benchmark run.

What happens

driftCheckApplies was extended to fire after a native Edit/Write/ MultiEdit/NotebookEdit — that was the whole point of the change — but driftCheck still passes the literal "Bash" to the logger.

Effect

The one channel that exists because warnings are invisible in the transcript now misattributes every native-edit warning to Bash. A benchmark measuring "which surface produced warnings" reads zero for the native path.

Fix

Thread event.ToolName into driftCheck and pass it through.

The warning channel

The contract's standing instruction is "act on any topology warning that comes back", and the warning channel is described as the one capability with no substitute. Both faults here are cases where it comes back empty and the code does not compile.

WARN-01

A signature change never warns about callers in the same file

HighReproduced

internal/topology/scanner/goscanner/scanner.go:479 if _, isOld := oldFunctions[FunctionID(callerID)]; isOld { continue } · internal/helper/referrers.go:231 if skipPaths[res.Location.Path] { continue } (called from manager.go:859 with skipPaths = {editedFile})

Requirements

Any language, any mode. Change a declaration's signature in a file that also contains one of its callers. Universal: two independent code paths implement the same skip — goscanner for Go, and ExpandSignatureWarnings for Python, JS, TS, Rust and Java.

What happens

Both producers deliberately exclude referrers declared in the file being re-parsed, on the reasoning that the re-parse is authoritative for that file. That reasoning holds for node_removed — confirmed: deleting the callee does raise use_missing_node against the same-file caller — because the symbol is gone and the re-parse notices the dangling reference.

It does not hold for a signature change. The symbol still resolves, so no use_missing_node is produced, and the skip removes the only other warning. Nothing is emitted at all.

Effect

The single most common shape of a breaking edit — widen a helper's parameter list, fix its callers afterwards — reports nothing when the caller happens to live beside it. The build is broken and both arac warnings list and the PostToolUse hook say "No warnings found".

Fix

Scope the skip to the warning kind. In goscanner, apply the isOld filter only in the removedFuncs loop (line 533), not in the signature-change loop (line 479). In ExpandSignatureWarnings, drop the skipPaths test entirely — it is only ever called with the edited file, and a caller inside it is exactly what needs verifying — or pass nil from manager.go:859. settleSignatureWarnings already retires these correctly once the call site fits, so nothing downstream needs to change.

Reproduction 
// pkg/sub/util.go — one file, callee and caller together
func Helper(a int) int { return a * 2 }
func SameFileCaller() int { return Helper(1) }

// widen Helper to (a int, b int), then PostToolUse Edit on that file:
(silent)
$ arac warnings list
No warnings found.
$ go build ./...
pkg/sub/util.go:10:16: not enough arguments in call to Helper

// move the caller to a second file and the warning appears:
[signature_changed] function Helper changed input/output format,
  verify caller example.com/proj/pkg/sub.UseHelper

// JavaScript behaves identically:
app.sameFileCaller    → no warning
other.crossFileCaller → warned
WARN-02

IndexHealth diffs only the languages already in the database

MedReproduced

internal/topology/indexhealth.go:139 languages := topo.Languages · contrast internal/topology/manager.go:138 langScanners := reg.DetectAll(root)

Requirements

Adding the first file of a language the topology does not yet contain — a first .py in a Go repo, a first .ts beside the JS.

What happens

IndexHealth takes its language list from the stored topology; IncrementalScan takes its from Registry.DetectAll against the tree. The comment says the primitive is shared "so what the status command reports, what a read blames a miss on and what an incremental scan would re-parse can never disagree" — the diff is shared, the language list is not.

Effect

arac check-updates prints "All files are up to date" and exits 0 with a whole unindexed language on disk — the one command whose job is answering "should I believe this graph". Inside the guard, indexHasDrifted returns false for the same reason, so the post-tool drift check skips its scan for the call that created the file; the model is one turn behind and the warnings, when they arrive, are attributed to a later command.

Fix

Union the stored languages with NewScannerRegistry().DetectAll(root) in IndexHealth, the way IncrementalScan does. A language present in the tree and absent from the manifest reports every one of its files as added, which is the honest answer.

Reproduction 
$ arac check-updates
All files are up to date.

$ cat > newlang.py <<'EOF'
def brand_new(a):
    return a + 1
EOF

$ arac check-updates
All files are up to date.        ← exit 0

$ arac scan
Incremental scan: processing only changed files
-6 functions                     ← it was there all along

Setup and the generated integration

All three of these are about the same promise, made in setup.go's own doc comment: "re-rendering must ask none, because it runs after a hand edit, in a script, in a Makefile, on a machine with nobody at the keyboard."

SETUP-01

arac setup silently skips every generated file that already exists, including the guard hook

HighReproduced

internal/cli/setup.go:679 writeMarkdownFile · internal/cli/setup.go:19 promptReplace · internal/cli/native_hooks.go:350 aracBinary

Requirements

Any re-run of arac setup without -y. Non-interactive runs (CI, a Makefile, < /dev/null) hit it unconditionally: ReadString returns EOF, the answer is read as "no", and the file is skipped.

What happens

writeMarkdownFile guards every generated file — the hook scripts, the agent markdown, the command markdown, the OpenCode plugins — behind a [y/N] prompt, while settings.json, .mcp.json, opencode.json and CLAUDE.md/AGENTS.md are rewritten unconditionally. So a re-run produces a half-updated integration, and says nothing is wrong.

The hook script is the sharp edge: arac-guard.sh embeds the absolute path of the binary that generated it (aracBinary(), resolved through filepath.EvalSymlinks). Rebuild elsewhere, move the binary, or install over a go install, and arac setup will not repoint it.

Effect

A stale binary path in a hook is not a quiet degradation — it is a failing subprocess on every tool call. Agent files drift the same way: this repository's own .claude/agents/descriptions-generation-executor.md still lists Edit, Write in its tools: and pins model: haiku, neither of which the current generator writes. That is precisely the generator/server drift ServableMCPTools and TestGeneratorMatchesServer exist to prevent, arriving through the file writer instead.

Fix

Stop asking for files aracne owns. arac setup regenerates its own artifacts; the prompt protects nothing, because the content is a pure function of the config. Either default autoYes to true for the generated set, or keep the prompt only for a file whose content differs from what the generator would write and whose difference is not aracne's own previous output. At minimum, treat a non-terminal stdin as "yes" the way confirmDisable already does (disable.go:302 — the two commands currently disagree about what an unattended run means).

Reproduction 
$ arac setup --claude -y            # first run, from /scratch/arac
$ cat .claude/hooks/arac-guard.sh
#!/bin/sh
exec /scratch/arac guard --claude-hook

$ cp arac arac2 && ./arac2 setup --claude < /dev/null
File .claude/commands/descriptions-generate.md already exists. Replace? [y/N]
  command descriptions-generate already present …, skipping
File .claude/hooks/arac-guard.sh already exists. Replace? [y/N]
  Claude guard hook script already present …, skipping
[Claude Code] Guard hook configured in .claude/settings.json      ← settings rewritten
[Claude Code] Restart Claude Code to activate the topology workflow.

$ cat .claude/hooks/arac-guard.sh
exec /scratch/arac guard --claude-hook   ← still the old binary
SETUP-02

arac setup will not add the MCP server when another server is already configured

HighReproduced

internal/cli/setup.go:395 shouldWriteConfig · internal/cli/setup.go:191 (Claude) · internal/cli/setup.go:109 (OpenCode)

Requirements

mode: mcp, and a .mcp.json that already has an mcpServers key — which is true of any project using any other MCP server, and true of every aracne project after its first setup.

What happens

shouldWriteConfig guards on the presence of the whole section, not on aracne's own entry, and asks "Config .mcp.json already exists. Overwrite?" — a question that misdescribes the action. With -y the code does not overwrite: it merges mcpServers["aracne"] and leaves every sibling untouched (verified). Answer "no", or run unattended, and the aracne server is simply never added.

Effect

Setup prints "[Claude Code] Restart Claude Code to activate the topology workflow" and writes a CLAUDE.md whose first section says "Aracne's capabilities arrive as MCP tools", against a .mcp.json with no aracne server in it. The model then spends turns looking for tools that do not exist — the exact failure the four-mode design exists to prevent, arriving through the generator.

Fix

Guard on aracne's own key, not the section: write when mcpServers["aracne"] is absent or differs from what the generator would produce, and never prompt for it — the entry is derived entirely from the config and the binary path. If a prompt is kept anywhere, its text must say what it will do ("Replace the existing aracne MCP server entry?").

Reproduction 
$ cat .mcp.json
{ "mcpServers": { "github": { "command": "gh-mcp" } } }

$ arac setup --claude < /dev/null   # mode: mcp
Mode: mcp — aracne serves a single `read` MCP tool; …
Config .mcp.json already exists. Overwrite? [y/N] [Claude Code] Skipping .mcp.json
…
[Claude Code] Restart Claude Code to activate the topology workflow.

$ cat .mcp.json
{ "mcpServers": { "github": { "command": "gh-mcp" } } }   ← no aracne

$ arac setup --claude -y   # with -y it MERGES; nothing is overwritten
{ "mcpServers": { "aracne": {…}, "github": { "command": "gh-mcp" } } }
SETUP-03

arac scan from a subdirectory forks a nested project with a default cli config

MedReproduced

internal/cli/scan.go:22 — the only verb whose default db path skips ProjectDBPath · contrast internal/cli/init.go:61, which refuses this case explicitly

Requirements

A plain arac scan run from any subdirectory of a configured project.

What happens

ProjectDBPath's doc comment describes this exact failure — "arac read from a subdirectory built a second, partial topology under <subdir>/.aracne/ … A project on intercept_line_ranges then answered those calls under cli semantics" — and every verb was moved onto it except arac scan, which still defaults -output to the literal relative path. arac init refuses the same situation with a pointer; arac scan creates it silently, and creates the .aracne/config.json even when the scan then fails.

Effect

Confirmed: after one such scan, <subdir>/.aracne/config.json exists with "mode": "cli", and guardDBPath's upward walk finds it first for anything running under that subtree. Interception stops for those paths and reads are answered from a partial graph. The hook (which prefers the session cwd) and arac cmd (which walks up from the agent's shell) can then resolve different databases for the same call, breaking the invariant that the hook and the verb must agree about what is modelled.

Fix

Route arac scan's default through ProjectDBPath/ProjectRootFor like every other verb, so a bare arac scan in a subdirectory scans the project it belongs to. Keep an explicit -output/-root literal, which is how someone deliberately sets a subdirectory up as its own project — the phrasing arac init's error already uses (arac scan -root .).

Reproduction 
$ python3 -c "print(json.load(open('.aracne/config.json'))['mode'])"
intercept_line_ranges

$ cd sub && arac scan
Analyzing project at: .
…
$ ls -a .aracne
config.json  file_manifest.json  topology.db

$ python3 -c "print(json.load(open('.aracne/config.json'))['mode'])"
cli                              ← the project's mode is gone for this subtree

$ arac cmd -- cat app.js  # served from the nested, partial graph
# guard PreToolUse for `cat app.js` here: (no rewrite)

OPENCODE-01

OpenCode has no interception at all, and its generated AGENTS.md promises it

HighReproduced

internal/cli/native_hooks.go:450 openCodePreToolScanPlugin (scan only) · internal/cli/native_hooks.go:500 openCodeNativeEditPlugin (edits only) · internal/prompts/contract.go:150 interceptHowItReaches · docs/modes.md — the mode table

Requirements

OpenCode, any mode. Most acute in intercept_id / intercept_line_ranges, where interception is the only read surface.

What happens

arac setup --opencode writes exactly two plugins: arac-pre-tool-scan.js, whose tool.execute.before runs arac guard --pre-scan and returns, and — only behind the edit-update-db-plugin flag no shipped path sets — arac-native-edit-sync.js. Neither rewrites a tool call. There is no OpenCode counterpart to interceptCommand.

Meanwhile the AGENTS.md generated for the same project reads: "Read files the way you normally would — cat, head -40, sed -n '80,120p'. When the target is indexed, the answer comes back enriched … grep is answered the same way." and "There is nothing to opt into and no second spelling to learn." None of it is true on this harness. docs/modes.md's table likewise marks shell grep "intercepted" in all four modes without a harness qualifier, and Config.InterceptGrep() returns an unconditional true.

The gap compounds: outside mcp mode initOpenCode writes "aracne_*": "deny" into the main agent's permission block, so an OpenCode project on intercept_line_ranges gives its main agent no MCP tools, no interception, and a contract that mentions no arac subcommand — aracne is inert and claims otherwise.

Effect

Every read and search instruction in the OpenCode contract is a promise the harness cannot keep, and the failure is invisible from both sides: the model gets plain cat output that looks normal, and aracne records nothing.

Fix

The mechanism exists. @opencode-ai/plugin's hook signature is "tool.execute.before"(input: {tool, sessionID, callID}, output: {args}) — verified in the vendored dist/index.d.ts at line 235 — and output.args is mutable, which is OpenCode's equivalent of hookSpecificOutput.updatedInput. Extend the existing plugin: when input.tool === "bash", shell out to a new arac guard --rewrite that takes the command on stdin and returns the rewritten command (reusing interceptCommand verbatim, so the two harnesses cannot drift), and assign it back to output.args.command.

Until that ships, the contract must not claim it: gate interceptHowItReaches/highInterceptHowItReaches and the grep sentence on the harness, and correct the mode table in docs/modes.md. A contract naming a capability the surface does not have is the failure contract.go's header says the file exists to prevent.

`grep` is answered the same way …

$ grep -n "output.args" internal/cli/native_hooks.go
(no matches — nothing rewrites a tool call)

FIDELITY-01

scan.ignore stops applying to a search whose root is not the topology root

MedReproduced

internal/topology/domain/ignore.go:135 relPath · internal/cli/cmd.go:381 and internal/cli/grep.go:62 BuildIgnoreMatcher(topo.Root, …)

Requirements

A non-empty scan.ignore, and a search run from a directory that is not the topology root — i.e. any search after the agent has cd'd, which is the case guardDBPath exists because of.

What happens

The matcher is built against the absolute topology root, but the walk emits paths relative to the process working directory. relPath resolves a relative input by joining it onto the matcher's root, so ../../generated/gen.go becomes <root>/../../generated/gen.go, filepath.Rel returns a ../ chain, and the function returns "" — which every rule reads as "outside the root, no rule applies".

Effect

Ignored trees — build output, generated code, vendored bundles — reappear in intercepted searches the moment the shell is not at the project root. The topology never indexed them, so the matches carry no annotation and no node; they are pure noise the project asked to be rid of.

Fix

In relPath, resolve a relative path against the process working directory (filepath.Abs) before making it root-relative, rather than joining it onto m.root. Every caller already hands the matcher paths from a real walk, so Abs is the correct base in all of them.

Reproduction 
scan.ignore: ["generated/"]  ·  generated/gen.go contains MAGICTOKEN

$ arac cmd -- grep -rn MAGICTOKEN .          # from the project root
(no matches, exit 1 — correct)

$ cd pkg/sub
$ arac cmd -- grep -rn MAGICTOKEN ../../
../../generated/gen.go:4:func GenThing() string { return "MAGICTOKEN" }
exit 0 — the ignored tree is back
FIDELITY-02

Passthrough uses LookPath, so it bypasses shell functions and aliases

LowReproduced

internal/cli/cmd.go:590 passthrough · internal/cli/cmd.go:136 commandIsAvailable

Requirements

A modelled command word that the user's shell resolves to a function or alias rather than to the binary on PATH.

What happens

arac cmd receives argv from the shell and, when it cannot serve the request, runs exec.LookPath(argv[0]). A shell function is invisible to LookPath, so the fallback runs a different program than the shell would have.

This is not hypothetical on the target harness: Claude Code installs a grep shell function that re-executes the CLI as ugrep with a fixed flag set. On this machine grep --version reports ugrep 7.8.4 while /usr/bin/grep is GNU grep 3.11 — two different dialects and two different flag surfaces behind one word.

Effect

The "byte-identical passthrough" guarantee in docs/architecture.md §7B does not hold for any wrapped command. A flag the wrapper supports and the base binary does not comes back as a usage error attributed to a command the model typed correctly.

Fix

There is no clean way to re-enter the caller's shell function from a child process, so the honest fix is to narrow the claim and detect the case: if $BASH_FUNC_<name>%% is exported, or the command word differs from what LookPath finds, decline to serve the command at all (return KindPassthrough before the rewrite) so the shell runs its own function. Failing that, soften §7B: byte-identical to the binary on PATH, not to the shell's resolution.

FIDELITY-03

Intercepted grep strips the ./ prefix real grep echoes

LowReproduced

internal/topogrep/grep.go:1314 displayPath (filepath.Rel(".", path))

Requirements

grep -rn pattern . — the most common recursive form.

What happens

Real grep echoes the operand it was given, so a match under . is reported as ./pkg/sub/util.go:3:…. displayPath normalises to pkg/sub/util.go:3:….

Effect

Cosmetic in isolation, but it is a string difference in the field a pipeline reads, in an answer the guard has already decided is a safe substitute. Anything comparing paths across the two forms sees a mismatch.

Fix

Echo the root as given: when the search root the caller typed begins with ./, prefix the display path with it, the way displayRoot already preserves the caller's spelling for the header line.

Contract and documentation drift

The contract is a shipped artifact — it is re-sent to the model on every request — so a wrong sentence in it is a defect, not a typo. DOCS-01 is the one that costs turns.

DOCS-01

The high contract documents a # CONTEXT: format the renderer never emits

MedReproduced

internal/prompts/contract_high.go:258-266 highReadOutput · internal/llm/languages/readunit/render.go:57 withLocations

Requirements

mode: intercept_line_ranges and contract_verbosity: high.

What happens

The contract tells the model each CONTEXT entry is "keyed by the exact span the declaration occupies" and shows ## src/shapes.rs:12-48 Circle: Description. withLocations does not replace the id with the span — its comment says so explicitly: "The id is kept alongside the span rather than replaced" — so the real line is ## example.com/proj.Greet (main.go:6-8): Greet says hello.

Two consequences. The documented shape is wrong, and the mode whose stated purpose is to stop teaching resource IDs leads every context entry with one — highLineRanges's comment says "nothing this mode renders may" teach ID vocabulary.

Effect

A model told to expect a span-first line and shown an id-first one has to re-derive the format from the output, which is the cost the long contract is paid to avoid. Whichever way it is resolved, the documented example and the renderer must agree.

Fix

Decide once and pin it with a test. Either update the example in highReadOutput to ## <id> (path:start-end): Description, or make withLocations emit the span alone under LineRangeIdentification — the mode already argues for the second. A golden-file test rendering one read per mode against the contract's own example would hold the two together; nothing currently does.

Reproduction 
contract (AGENTS.md / CLAUDE.md, high + intercept_line_ranges):
# CONTEXT:
## src/shapes.rs:12-48 Circle: Description
    src/shapes.rs:50-58 Circle::new: Description

actual output of `arac cmd -- tail -3 main.go`:
# CONTEXT:
## example.com/proj.Greet (main.go:6-8): Greet says hello.

DOCS-04

A comment claims existingReadFiles resolves against the process cwd; it does not

LowFrom source

internal/cli/guard_intercept.go:228 (the claim) · internal/cli/guard_untracked.go:78 (the code)

Requirements

Reading the interception code to reason about path resolution.

What happens

namesOnlyUnindexedFiles's comment says the resolver "tries each token against the project root as well as the process cwd". It does not: a token is used as-is only when it is already absolute, and otherwise joined onto the project root. Nothing consults the process cwd.

Unconfirmed — needs a harness to settle

Three things I could not verify from inside this repository, each with a large blast radius if it turns out to be wrong. They are not counted in the tally above. Each can be settled in minutes with a live session.

  • Does Claude Code read mcpServers: from sub-agent frontmatter? Every generated Claude sub-agent declares its own scoped server inline (setup.go:514, claudeMCPServersFrontmatter), as a YAML list of single-key maps rather than the object shape MCP configs normally take. docs/architecture.md §9 rests the whole "the descriptions and bug pipelines keep working on the terminal surface" argument on it. If the key is not read, those agents get an empty tool list in three of the four modes and the failure is silent. To settle: run /descriptions-generate in a non-mcp project and check whether the executor can call update_description.
  • Does OpenCode load .opencode/agents, commands, plugins (plural)? Aracne writes all three plural (setup.go:148-150, native_hooks.go:441). If OpenCode's convention is singular (.opencode/agent, command, plugin), none of the generated OpenCode artifacts are loaded at all — including the pre-tool scan plugin, which would make scan.pre_tool a no-op on that harness. The vendored @opencode-ai/plugin types do not encode directory conventions, so this needs the running product.
  • Is "shell": "bash" a real field in a Claude Code hook entry? Written on every hook entry (native_hooks.go:47, 97). Harmless if ignored; worth confirming it is not rejected by a stricter settings validator, since a rejected entry takes the whole guard down.

Method. Built cmd/arac at a882cd3 into a scratch directory, created two throwaway fixtures (a Go module with a cross-package caller, a CommonJS project with a cross-file caller), and drove arac guard --claude-hook with hand-written PreToolUse/PostToolUse event JSON — the same shape Claude Code sends, including the cwd field — rather than through a live session, so each decision could be isolated. Searches were diffed against /usr/bin/grep directly; the shell's grep on this machine is a Claude Code wrapper function around ugrep, and comparing against it produced misleading results early on (see FIDELITY-02).

What is not here. The viz Chat tab, internal/chat, arac agent and the benchmark harness were out of scope. The language scanners were exercised only where a fault in the harness path led into them; the testing_ground corpus and the at-scale suites were left to their own tests. No code was changed.
