H1A project path containing a space kills every hook

internal/cli/native_hooks.go:249,256,312,319 · writeClaudeGuardHook

FIXED — quoted, and verified from a path with a space
bashHookCommand / powershellHookCommand now wrap the script path ("…" for bash, & '…' for PowerShell, which needs the call operator alongside the quotes). hookCommandWord was added so a quoted command is still recognized as aracne's own — otherwise arac setup would stack a duplicate beside it and arac disable would leave it behind. Verified end to end: the guard now runs and rewrites from /…/my proj, where it previously exited 127. Pinned by TestHookCommandSurvivesAPathWithSpaces and TestHookCommandWord.
What happens
arac setup writes the hook into settings.json in shell form with an unquoted placeholder: 
"command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/arac-guard.sh",
"shell":   "bash"
Claude Code expands ${CLAUDE_PROJECT_DIR} to the project root and hands the string to bash -c. A root containing a space word-splits, so the hook never runs. The Claude Code hooks reference is explicit about this: “Prefer exec form for any hook that references a path placeholder. In shell form, wrap each placeholder in double quotes.”
Requirements
Any project whose absolute path contains a space or any other word-splitting character — ~/My Projects/…, ~/Library/Mobile Documents/…, a Windows C:\Users\First Last\… under Git Bash. Extremely common on macOS and Windows.
Effect
The guard is completely dead and fails loudly on every single tool call: no interception, no scan.pre_tool freshness scan, no blocked_tools enforcement, no PostToolUse nudge, no drift check. The user sees a hook error on every turn. Nothing in aracne detects or reports this.
Reproduction
verbatim
$ mkdir -p "/tmp/scratch/my proj" && cd "/tmp/scratch/my proj"
$ arac scan && arac setup --claude -y
$ export CLAUDE_PROJECT_DIR="/tmp/scratch/my proj"
$ bash -c "${CLAUDE_PROJECT_DIR}/.claude/hooks/arac-guard.sh" </dev/null
bash: line 1: /tmp/scratch/my: No such file or directory
exit=127

$ bash -c "\"${CLAUDE_PROJECT_DIR}/.claude/hooks/arac-guard.sh\"" </dev/null
exit=0
Fix
Switch to exec form, which removes the shell (and the shell field) entirely and is what the docs recommend for placeholder paths: 
entry := map[string]any{
    "matcher": guardHookMatcher,
    "hooks": []any{map[string]any{
        "type":    "command",
        "command": "${CLAUDE_PROJECT_DIR}/.claude/hooks/arac-guard.sh",
        "args":    []string{},          // <- exec form: no shell, no word splitting
        "timeout": 30,
    }},
}
Or, minimally, quote it: "\"${CLAUDE_PROJECT_DIR}/.claude/hooks/arac-guard.sh\"". Apply the same change to the arac-update-file hook. A regression test asserting the command string is either exec form or fully quoted belongs beside TestClaudeGuardHookForOS.

H2arac setup --global installs a hook that can never resolve

internal/cli/native_hooks.go:244-259 + internal/cli/setup.go:364-374 (claudePaths)

FIXED — the global install names the script it actually wrote
hookScriptRef(hooksDir, name, global) returns the portable ${CLAUDE_PROJECT_DIR} form for a project install and the absolute path for --global. global is threaded through writeClaudeGuardHook, writeClaudeNativeEditHook and writeClaudePlugins. Verified: arac setup --claude --global against a temp HOME now writes a command whose target exists on disk. Pinned by TestGlobalHookNamesTheScriptItActuallyWrote, which also asserts a local install keeps the placeholder.
What happens
With --global, claudePaths(true) returns ~/.claude/commands, so claudeBaseDir is ~/.claude. The script is written to ~/.claude/hooks/arac-guard.sh and the entry to ~/.claude/settings.json. But claudeGuardHookForOS hard-codes the command as ${CLAUDE_PROJECT_DIR}/.claude/hooks/arac-guard.sh — and ${CLAUDE_PROJECT_DIR} is documented as “the project root where the session started”, not the home directory. The command points at a file that was never written.
Requirements
arac setup --global (or arac init --global) in any project that does not also have a local .claude/hooks/arac-guard.sh. That is the entire point of a global install, so it is the normal case.
Effect
Same as H1 — the guard never runs — but silently for a user who deliberately chose the “install once, works everywhere” path. The same bug applies to the arac-update-file hook (native_hooks.go:312,319).
Fix
Thread the global flag into claudeGuardHookForOS / claudeNativeEditHookForOS and use the real script path when it is set. Since aracBinary() already resolves an absolute binary path at setup time, the simplest correct form is to drop the wrapper script for the global case and point the hook straight at the binary in exec form: 
"command": aracBinary(),
"args":    []string{"guard", "--claude-hook"},
which is correct for both scopes and also fixes H1.

H3A native edit produces no topology warning — and the warning that eventually arrives blames the wrong command

internal/cli/guard.go:158 · internal/cli/guard_drift.go:150 · internal/cli/plugins.go · helper.DefaultConfig

FIXED — warnings arrive on the edit that caused them, and the header no longer lies
Three changes. (1) driftCheckApplies replaces the Bash-only condition and now covers native Edit/Write/MultiEdit/NotebookEdit, asking toolspec.NativeToolKey rather than listing names. (2) The drift header is now "Topology re-synced." — the reporter reports what is new in the table however it got there, so it is in no position to blame a shell command. (3) runClaudeUpdateFileHook now reports through the same unreportedWarnings ledger and resolves its database with guardDBPath(event.cwd), so enabling the edit-sync plugin cannot double-report and the hook can no longer create a stray .aracne/ outside the project (that last part also closes M5). Verified: the signature break is now reported on the native Edit's own PostToolUse, once, and a later ls adds nothing. Pinned by TestDriftCheckCoversNativeEdits, TestDriftWarningsDoNotBlameAShellCommand and TestUpdateFileHookNeverBuildsATopology.
What happens
Two things compound:
  • The arac-update-file PostToolUse hook — the only thing that reports warnings after a native Edit/Write/MultiEdit — is installed only when the main agent lists the edit-update-db-plugin plugin. Nothing ever sets it. DefaultConfig() leaves plugins empty, arac init never asks about it, and this repository's own .claude/settings.json has no such hook.
  • The guard's own drift check is gated on event.ToolName == "Bash" (guard.go:158), so it never fires for a native edit either.
The warning is still created — by the next tool call's scan.pre_tool scan — and then delivered by the next Bash command that happens to be unclassified, under the header "Topology re-synced after a shell command wrote to the project."
Requirements
Any default install (arac init or arac setup with a stock config) where the model uses the native Edit/Write tool. That is the default editing path in Claude Code, and blocked_tools ships empty.
Effect
The generated contract, in every mode, tells the model: “Your edits keep the graph current automatically; act on any topology warning that comes back.” For a native edit no warning ever comes back at the time of the edit. When one does surface, it is attached to an unrelated command and asserts a falsehood — that a shell command wrote to the project. A model that trusts the attribution will look for a shell write that never happened. Worse, if the next Bash call is classified (a cat, a grep), the drift check is skipped and the warning may not surface for many turns, or at all.
Reproduction
Fixture: pkg/util.go declares Helper; main.go calls it. Mode intercept_line_ranges, stock config.
verbatim
# 1. PreToolUse for the native Edit (seeds warn-state, runs the pre-scan)
$ echo '{"hook_event_name":"PreToolUse","tool_name":"Edit",
         "tool_input":{"file_path":".../pkg/util.go"},"cwd":".../proj"}' | arac guard --claude-hook
(no output)

# 2. the edit lands: func Helper(x int) -> func Helper(x, y int)

# 3. PostToolUse for the native Edit
$ echo '{"hook_event_name":"PostToolUse","tool_name":"Edit", ...}' | arac guard --claude-hook
{"hookSpecificOutput":{"additionalContext":
  "aracne: `echo '{\"edits\":[…]}' | arac edit` applies several replacements in ONE call...",
  "hookEventName":"PostToolUse"}}
$ arac warnings list
No warnings found.                      <-- nothing found, nothing reported

# 4. an entirely unrelated later call: `ls`
$ echo '{"hook_event_name":"PreToolUse","tool_name":"Bash",
         "tool_input":{"command":"ls"}, ...}' | arac guard --claude-hook
$ arac warnings list
  [signature_changed] function Helper changed input/output format,
                      verify caller example.com/proj.main

$ echo '{"hook_event_name":"PostToolUse","tool_name":"Bash",
         "tool_input":{"command":"ls"}, ...}' | arac guard --claude-hook
{"hookSpecificOutput":{"additionalContext":
  "Topology re-synced after a shell command wrote to the project.\n
   Topology warnings (functions that may need manual review):\n
     - [signature_changed] function Helper changed input/output format, ...",
  "hookEventName":"PostToolUse"}}

ls wrote nothing. The message says it did.

Fix
Three independent changes, each worth making:
  1. Run the drift check for native edits. In guard.go's PostToolUse branch, extend the condition past Bash: 
    if (event.ToolName == "Bash" && mayHaveWrittenSource(keys) && !isAracCommand(event.ToolInput)) ||
   toolWritesSource(event.ToolName) {   // Edit | Write | MultiEdit | NotebookEdit
    if msg := driftCheck(dbPath); msg != "" { parts = append(parts, msg) }
}
    toolspec.nativeToolToKey already knows which native tools mean edit.
  2. Make the header honest. formatDriftWarnings should not assert a cause. “Topology re-synced. Topology warnings (functions that may need manual review):” says the true thing in the same bytes.
  3. Decide the plugin default. Either add edit-update-db-plugin to DefaultConfig()'s main agent (so the promise in the contract is kept out of the box) or stop making the promise. Today the config and the contract disagree.

H4arac cmd answers for binaries that are not installed

internal/cli/cmd.go:75 (serveCommand) — no exec.LookPath gate

FIXED — a command the shell could not have run is passed through
serveCommand gates on commandIsAvailable(argv[0]) before it opens the topology, with one exemption: Get-Content is a PowerShell cmdlet and is never on PATH. Verified on this host (no ripgrep, bat or ack): arac cmd -- rg Add now returns arac cmd: rg: command not found and exit 127, byte-identical to the real failure, while grep and cat are still served. Pinned by TestCmdRefusesACommandTheShellCouldNotRun and TestCommandAvailabilityExemptsShellResolvedCommands.
What happens
serveCommand classifies argv with shellcmd.Parse and, if it recognises the shape, answers it from the topology. It never checks that argv[0] is a command the shell could actually have run. So on a machine without ripgrep, rg <pattern> returns a full annotated search and exits 0. The guard rewrites the model's rg into arac cmd -- rg, so the model never sees the truth.
Requirements
Any machine where rg, ack, ag, ug, bat, egrep/fgrep or get-content is absent — i.e. most container images and most stock Linux boxes for rg/bat/ack. Applies in every mode for the search commands, and in the two intercepting modes for the readers.
Effect
aracne manufactures a capability that does not exist and then withdraws it without warning. The model concludes ripgrep is available; the first rg carrying a flag shellcmd does not model (-o, --files, --hidden, --json, -U, …) falls through to passthrough() and returns command not found, exit 127. This is precisely the failure the shellcmd package doc exists to prevent — “a wrong answer wearing a helpful face” — arriving from the other direction.
Reproduction
verbatim (ripgrep, bat and ack are all absent on this host)
$ which rg bat ack
(nothing)

$ arac cmd -- rg Add
# pkg/util.go:4-6 — Adder adds numbers.
pkg/util.go:4:type Adder struct {
# pkg/util.go:9-12 — Add adds n to the total.
pkg/util.go:9:func (a *Adder) Add(n int) int {
exit=0

$ arac cmd -- bat main.go
```main.go
package main
...
exit=0

$ arac cmd -- rg -o Add
arac cmd: rg: command not found
exit=127
Fix
One gate at the top of serveCommand, after the passthrough classification: 
req := shellcmd.Parse(argv)
if req.Kind == shellcmd.KindPassthrough {
    return "", 0, nil, false
}
// aracne answers a command IN PLACE OF the real one. A command that would not have
// run is not a question aracne was asked -- passthrough reproduces its exact error.
if _, err := exec.LookPath(argv[0]); err != nil {
    return "", 0, nil, false
}
passthrough() already produces the byte-identical arac cmd: rg: command not found / exit 127 that the shell would have. Optionally add the same check to interceptableSegment so the rewrite is skipped too — it is not required for correctness, but it saves a subprocess.

M1grep -H / --with-filename is silently ignored

internal/shellcmd/shellcmd.go:675 (accepted and discarded) · internal/topogrep/grep.go:597-608 (bare := opt.Terse && res.RootIsFile)

FIXED — -H and --with-filename are honoured
shellcmd.GrepRequest and topogrep.Options carry WithFilename; the renderer's bare test now reads Terse && RootIsFile && !WithFilename. Verified against GNU grep 3.11: grep -H -n Total pkg/util.go now prints pkg/util.go:5: as the real command does. topogrep.RawBytes was taught the same two shape questions, so the over-serve denominator still describes a row the caller actually sees. Pinned by TestFilenameAndLineNumberFlagsAreCarried (shellcmd) and TestGrepHonoursExplicitFilenameAndLineNumberFlags (five flag combinations against the real grep).
What happens
parseGrep lists -H/--with-filename among the flags that are “accepted and ignored”, on the stated grounds that “aracne always reports path:line”. That is not true on the shell surface: FormatResult sets bare = Terse && RootIsFile and then omits the path for a single-file operand. topogrep.Options carries no field for “the caller asked for the filename”, so the information is destroyed at parse time and cannot be recovered.
Requirements
grep -H … (or --with-filename) with exactly one file operand, on any surface that sets Terse — i.e. every intercepted shell search, in every mode.
Effect
Output shape changes under the caller. grep -H -n pat f | cut -d: -f1 is a list of paths to the real grep and a list of line numbers to aracne. Interception explicitly permits piping a search into line filters (ConsumerLineFilter), so this is reachable in a pipeline aracne volunteered to answer.
Reproduction
GNU grep 3.11
$ /usr/bin/grep -H -n Total pkg/util.go
pkg/util.go:5:  Total int
pkg/util.go:10: a.Total += n
pkg/util.go:11: return a.Total

$ arac cmd -- /usr/bin/grep -H -n Total pkg/util.go
# pkg/util.go:4-6 — Adder adds numbers.
5:      Total int
# pkg/util.go:9-12 — Add adds n to the total.
10:     a.Total += n
11:     return a.Total

Same for --with-filename. (Note: plain -r with a single file operand does match GNU grep — GNU only implies -H when more than one file is searched. Only the explicit flag is lost.)

Fix
Add WithFilename bool to shellcmd.GrepRequest and topogrep.Options, set it on -H/--with-filename, and make the renderer bare := opt.Terse && res.RootIsFile && !opt.WithFilename. Then remove -H from the “accepted and ignored” branch's comment, since it is no longer ignored. Note that tests/grep_parity_test.go cannot catch this today: it forced -H onto the reference grep and re-attached the implied path to aracne's bare rows, normalising the difference away — that harness now passes the same flags to both sides.

M2Line numbers are emitted whether or not -n was asked for

internal/topogrep/grep.go:596-608 — the emit closure always writes %s:%d:%s

FIXED — line numbers only when -n asked for them
Same mechanism: LineNumbers is carried from the parsed flag on the shell surface and defaults to true for the MCP/CLI surfaces, which have no -n to honour. Verified: grep -r Add pkg now prints pkg/util.go:// Adder…, matching GNU grep, instead of injecting a line-number column the caller did not ask for.
What happens
There is no code path that renders a match without its line number. shellcmd accepts -n and throws it away because the renderer “always” prints it — which means a grep that did not ask for line numbers gets an extra colon-delimited field.

Any intercepted search without -n/--line-number. Agents type this routinely: grep -rl, grep -r pat dir, grep -c are the common shapes, and only the first two reach the content renderer.
Effect
A field the caller did not ask for is injected in the middle of every row, shifting every later field. grep -r pat dir | cut -d: -f2- returns the match text to the real grep and line:text to aracne. Same class as M1, and it is the more common shape.
Reproduction
GNU grep 3.11
$ /usr/bin/grep -r Add pkg
pkg/util.go:// Adder adds numbers.
pkg/util.go:type Adder struct {
pkg/util.go:// Add adds n to the total.
pkg/util.go:func (a *Adder) Add(n int) int {

$ arac cmd -- /usr/bin/grep -r Add pkg
# pkg/util.go:4-6 — Adder adds numbers.
pkg/util.go:4:type Adder struct {
# pkg/util.go:9-12 — Add adds n to the total.
pkg/util.go:9:func (a *Adder) Add(n int) int {
Fix
Carry LineNumbers bool the same way as M1's WithFilename, defaulting to true for the MCP/CLI surfaces (which have no -n to honour) and to the parsed flag for the shell surface. If that is judged too invasive, the honest alternative is the one the package's own doc prescribes: make a search without -n a KindPassthrough. Silently changing the column layout is the one option the package rules out.

M3The PostToolUse nudge fires for files the topology does not model — and the guard already has the check it needs

internal/cli/guard_intercept.go:226-248 (namesAnIndexedFile, never called) · internal/cli/guard.go:131-136

FIXED — the guard now calls the check it already had
worthNudging gates the native read/search pointer on namesAnIndexedFile — which existed, documented the exact regression it prevents, and had no callers. A mutation is still nudged unconditionally: its guidance is about the topology sync, and an edit that creates a file's first declaration would fail an index test. Verified: a native Read of CHANGELOG.md (zero nodes) is now silent; one of main.go still gets the pointer. Pinned by TestNudgeRequiresSomethingToOffer.
What happens
namesAnIndexedFile exists, carries a 20-line doc comment describing the exact regression it was written to prevent, cites a real smoke-cell failure — and has no callers. Confirmed with a repo-wide search: the only other occurrences of the name are inside its own comment. The PostToolUse branch calls warningMessage(keys, …) unconditionally.
Requirements
A native Read/Grep/Edit/Write on any file with no topology nodes: CHANGELOG.md, README.md, a lockfile, a template, a YAML config, anything in an unsupported language. Every mode.
Effect
The model is told, on every such call, that “cat, head -N, tail -N and sed -n 'A,Bp' on an indexed file are answered from the topology” — for a file that is not indexed and where aracne has nothing to add. The nudge text is injected into the transcript on every matching call; toolspec's own comment budgets it at “~16 KB across eighty native calls”. {"hookSpecificOutput":{"additionalContext":
  "aracne: `cat`, `head -N`, `tail -N` and `sed -n 'A,Bp'` on an indexed file are
   answered from the topology -- the lines you asked for, framed by their declaration,
   with the exact range of everything they touch.","hookEventName":"PostToolUse"}}

# byte-identical output for an indexed file — the check never runs

Call it. In the event.ToolName != "Bash" branch, gate the read/grep guidance on evidence: 
case event.ToolName != "Bash":

    }

M4arac disable silently leaves the contract behind when its closing line was edited

internal/cli/disable.go:426 (stripAracneIntegrationSegment) vs internal/cli/setup.go:765 (updateMarkdownIntegrationSegment)

FIXED — one bounds helper for the writer and the remover
aracIntegrationBounds is now the single answer to "where is the block", including the fallback to the next top-level heading when the closing line was edited away. updateMarkdownIntegrationSegment and stripAracneIntegrationSegment both call it, so they cannot disagree again. Verified: arac disable now removes an edited block and leaves the reader's own content. Pinned by TestDisableRemovesABlockMissingItsClosingLine.
What happens
The generated block has no delimiter — it is found by its opening heading and by whichever real closing sentence the contract ends on. arac setup handles the case where a reader has edited that last sentence away: it falls back to nextTopLevelHeading and replaces up to there, with an explicit comment about why. arac disable has no such fallback. When findAracIntegrationEnd returns -1 it returns the content unchanged, and the caller prints “CLAUDE.md already clean”.
Requirements
Anyone who edits or deletes the contract's last line — which reads as ordinary prose in a file they are told is theirs — and then runs arac disable. Also reachable after a partial upgrade, since the closing line differs per mode.
Effect
An uninstall that reports success and removes nothing, leaving the whole contract in CLAUDE.md / AGENTS.md — still re-sent on every request, now describing an integration that no longer exists (the MCP entry, hooks and agents were removed). The “already clean” message actively misleads.
Reproduction
verbatim
$ arac setup --claude -y
$ # user deletes the last line ("Parallelise multiple reads and edits ...")
$ arac disable --claude -y
Claude Code CLAUDE.md already clean at CLAUDE.md

$ cat CLAUDE.md
# My own section

# Aracne

This repository supports Aracne: every function, type, interface and variable is indexed...
...
(the whole block still there)
Fix
Give the remover the writer's fallback: 
end, endMarker := findAracIntegrationEnd(content, start)
if end < 0 {
    // Same rule as updateMarkdownIntegrationSegment: a block whose closing line the
    // reader removed runs to the next top-level heading, or to end of file.
    return strings.TrimRight(content[:start], " \t\r\n") +
           tail(content, nextTopLevelHeading(content, start), lineEnding)
}
Both functions should share one aracIntegrationBounds(content) (start, end int, ok bool) helper so the writer and the remover cannot disagree about where the block is again.

M5The update-file hook ignores the event cwd, and creates a stray .aracne/ outside the project

internal/cli/update_file.go:42-60 · internal/cli/helpers.go:87 (InitRegistry)

FIXED — fixed alongside H3
runClaudeUpdateFileHook resolves its database with guardDBPath(event.cwd) — the guard's own three-tier ladder — and returns when there is no topology instead of letting InitRegistry build one. Verified: run from outside the tree it now creates no .aracne/ and says nothing. Pinned by TestUpdateFileHookNeverBuildsATopology.
What happens
guardDBPath exists precisely because a hook's working directory is not dependable; its doc comment describes a benchmark run lost to exactly this. It resolves in three tiers: the hook event's cwd, then $CLAUDE_PROJECT_DIR, then an upward walk. runClaudeUpdateFileHook — the sibling hook, on the same surface, receiving an event JSON that carries the same cwd field — parses only tool_input and resolves with ProjectDBPath(DefaultDBRelative), which is the upward walk alone. When that finds nothing, InitRegistry does not bail: it MkdirAlls a .aracne/, prints “No topology found. Scanning project...”, and os.Exit(1)s.
Requirements
The hook process running anywhere that is not inside the project — a session whose Bash cwd moved outside the tree, a worktree/temp directory that vanished (Claude Code then falls back to the session dir, the project root, $HOME, or the system temp dir), or a monorepo edited from outside its indexed subtree.
Effect
The real topology is never re-synced for that edit; a junk .aracne/ directory is left in an unrelated location; the hook exits non-zero. And if that directory ever does acquire a database, later arac cmd calls run there will answer from the wrong topology.
Reproduction
verbatim
$ mkdir /tmp/outside && cd /tmp/outside
$ echo '{"tool_name":"Edit","tool_input":{"file_path":"/tmp/proj/pkg/util.go"}}' \
  | arac update-file --claude-hook
No topology found. Scanning project...
Error scanning project: no language scanner detected for /tmp/outside
$ ls -a /tmp/outside
.  ..  .aracne         <-- created, empty, never asked for
Fix
Decode cwd from the event and use the guard's own resolver: 
var event struct {
    ToolInput map[string]interface{} `json:"tool_input"`
    Cwd       string                 `json:"cwd"`
}
...
dbPath := guardDBPath(event.Cwd)
if _, err := os.Stat(dbPath); err != nil {
    return  // no topology here: a hook has nothing to do, and must not build one
}
manager := topology.New()
if err := manager.Load(dbPath); err != nil { return }
Separately, InitRegistry's unconditional os.MkdirAll(filepath.Dir(dbPath)) is worth revisiting on its own account: every CLI verb creates .aracne/ wherever it is run, before it knows whether there is anything to put in it.

M6The contract block is spliced between the host document's title and its body

internal/cli/setup.go:853 (markdownIntegrationInsertionIndex)

5  Deliberate deviations worth a decision

Not bugs — each is documented in a code comment as intended. Listed because each one changes what a command means, and a release is the moment to confirm the trade.

-m N is a cap on line matches only
searchFile deliberately keeps collecting node rows past the cap. Measured: grep -m 1 -n Add pkg/util.go returns 1 row from GNU grep and 3 from aracne (two node rows plus the line hit). Node rows are budgeted (NodeHitBudget, 25% of the head limit) so it cannot run away, but grep -rm 1 foo . — the “one hit per file, an index of the tree” idiom shellcmd explicitly protects — no longer returns one row per file.
Matches are re-ordered by tier
Title hits, then description hits, then line hits — not file order. Interception permits piping a search into head, so grep … | head -20 returns a different twenty lines than the real command would. The annotation lines are counted in that twenty too.
The ./ prefix is dropped for a . root
GNU grep prints ./pkg/util.go:3:…; aracne prints pkg/util.go:4:…. tests/grep_parity_test.go normalises this away explicitly. Same pipeline-fidelity class as M1/M2, but a smaller blast radius.
Searches prune directories grep would walk
prunedDirs skips .git, .aracne, node_modules, vendor, .venv, .next, … A grep -rn X . that the real command answers with a vendored hit comes back empty, with nothing in the output to say a directory was skipped.
OpenCode gets the MCP server enabled in every mode, with the main agent denied every tool
initOpenCode writes mcp.aracne.enabled: true unconditionally (the sub-agents need it) and then "aracne_*": "deny" for the main agent, with no allow entries outside mcp mode. If OpenCode lists a denied tool's schema to the model — I could not verify either way — the terminal-surface modes pay a schema block per request for eight tools the main agent may never call, which is the cost those modes exist to avoid. Worth confirming against a real OpenCode session before release.
A whole-file cat of a small file costs more than cat
The over-serve floor is 12 KB, so short files always come back with the fence and the group header on top. Intended (the floor exists so a narrow window can expand to its declaration), but it means the very cheapest read is slightly more expensive than the command it replaced.
